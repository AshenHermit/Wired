# План: база мультиплеера и синхронизации Godot

Дата: 2026-10-28

## Цель

Подготовить Wired к совместной игре в Godot-комнате:

- при подключении первого пользователя запускать выделенный серверный процесс
  Godot для комнаты;
- показывать игру во вкладке Game как браузерную Godot Web-сборку;
- подключать игровой клиент к серверу своей комнаты для мультиплеера;
- позволять создавать в Godot-проекте комнаты несколько пакетов
  пользовательского контента: каждый пакет — отдельная папка с файлами,
  собственным ID и ревизиями; сохранять содержимое каждого пакета на backend;
- по нажатию Emit публиковать ревизию выбранной папки-пакета и доставлять её
  серверу и игровым клиентам этой комнаты;
- выключать процесс сервера после длительного отсутствия пользователей,
  предварительно сохранив состояние игры средствами Godot-проекта.

Сейчас целевой этап — локальная разработка. Права редактирования пакетов и
комнаты пока не реализуются, но будущая авторизация действий должна быть
предусмотрена в границах API.

## Зафиксированные решения

1. **Сервер комнаты запускается при первом подключении игрового клиента**
   (вкладка Game), а не при создании комнаты или открытии редактора. Backend
   управляет жизненным циклом серверного процесса.
2. **Сервер останавливается после длительного простоя.** Перед остановкой
   Godot-проект сохраняет состояние игры. Таймаут простоя должен быть
   конфигурируемым.
3. **Контент пакета передаётся отдельными файлами**, а не единым PCK/архивом.
   Сервер и клиенты загружают файлы пакета из хранилища Wired.
4. **Emit публикует версию пакета**, после чего сервер комнаты и активные
   клиенты получают уведомление, загружают необходимые файлы и применяют
   одну и ту же версию.
5. **Пока всё работает локально.** Не вводить на этом этапе облачное
   масштабирование, многопользовательское редактирование пакетов или полную
   систему ролей. Не строить архитектуру так, чтобы будущую проверку прав
   пришлось обходить: все изменяющие операции должны идти через backend API.
6. **Игровой транспорт — `WebSocketMultiplayerPeer`.** Godot Web-клиент
   подключается непосредственно к Godot-серверу комнаты; игровой трафик,
   RPC и синхронизация состояния идут через `MultiplayerAPI`. Файлы пакетов
   передаются отдельно по HTTP, не через игровые RPC.
7. **Локальная маршрутизация — отдельный порт на комнату.** Backend
   резервирует порт и запускает сервер комнаты на нём. Для будущего
   размещения целевой вариант — `wss://` через reverse proxy, который
   маршрутизирует соединение в нужный внутренний порт Godot; браузеру не
   следует открывать прямые внутренние порты production-сервера.

## Текущее состояние репозитория

- Frontend: Next.js. Вкладки Editor, Packages и Game находятся в
  `frontend/src/app/room/[room_code]/(godot)/RoomPageClient.tsx`. Game пока
  заглушка; Editor загружает Godot WASM-редактор, не игровую сборку.
- Вкладка Editor важна и для пакетов: пользователь создаёт и редактирует их
  файлы непосредственно в Godot-редакторе. Текущая интеграция сохраняет
  экземпляр `GodotEditorInstance` в `window.editor`; в кастомной сборке
  доступна виртуальная файловая система Emscripten через
  `window.editor.editor.rtenv.FS`. Frontend должен читать из неё изменённые
  файлы для отправки на backend и записывать в неё опубликованные обновления,
  полученные с сервера.
- Backend: NestJS, комнаты и пакеты хранятся через TypeORM/Postgres.
  Одна комната может содержать несколько `ScriptingPackage`; каждый пакет
  имеет отдельные метаданные, ID и ревизии. Пакетные метаданные включают
  список `physicalFiles`, сами файлы сохраняются в файловом хранилище.
  Не считать комнату пакетом и не объединять каталоги/ревизии разных пакетов.
- Модуль `packages/server/src/godot-game/godot-game.module.ts` пока пустой.
- В `packages/server/godot_project/_wired` есть стартовые Godot-скрипты
  `WiredServerNode` и `WiredClientNode`, создающие
  `WebSocketMultiplayerPeer`, и пустой `PackagesManager`. Это заготовка,
  а не завершённый сетевой или пакетный протокол.
- Локальный Godot executable для первоначального прототипа:
  `C:\Users\hermit\gamedev\godot-wired\godot\bin\godot.windows.editor.dev.x86_64.exe`.
  Путь должен задаваться конфигурацией, а не вшиваться в исходники.

## Целевая схема взаимодействия

1. Браузер во вкладке Game запрашивает у backend подключение к комнате.
   Открытие только вкладки Editor само по себе игровой процесс не запускает.
2. Backend находит или запускает серверный процесс Godot для комнаты,
   передавая ему конфигурацию комнаты и параметры начальной загрузки.
3. Backend сообщает клиенту состояние запуска и параметры подключения.
   Клиент подключается к игровому WebSocket-серверу комнаты.
4. Godot-сервер и игровые клиенты загружают опубликованные файлы пакетов
   через HTTP endpoints Wired. Godot-проект отвечает за применение контента
   внутри игры.
5. Emit создаёт опубликованную ревизию пакета на backend. Только после
   успешной фиксации файлов и манифеста backend сообщает Godot-серверу и
   активным редакторам о новой ревизии. Сервер применяет её для игры;
   frontend загружает файлы и обновляет ими виртуальную FS открытого
   Godot-редактора.
6. Backend отслеживает присутствие игроков. Когда активных пользователей
   нет дольше заданного таймаута, он просит Godot штатно сохранить состояние
   и завершиться, затем подтверждает остановку процесса.

Управление процессами, пакетами и состоянием комнаты идёт через HTTP API
backend. Для первой локальной версии frontend получает от API адрес
`ws://localhost:<port>` после того, как backend запустил Godot и подтвердил
готовность listener. Godot Web-клиент устанавливает
`WebSocketMultiplayerPeer.create_client(url)`, а сервер комнаты —
`WebSocketMultiplayerPeer.create_server(port)`; затем каждый назначает peer
в соответствующий `MultiplayerAPI`. Игровые сообщения и состояние
мультиплеера идут через Godot RPC/репликацию по этому соединению.

Клиент не должен считать соединение готовым только потому, что WebSocket
открылся: после подключения он проходит прикладное подтверждение с сервером,
и только затем сервер включает peer в игровую сессию. До подтверждения
разрешён только handshake; игровые RPC и действия должны отклоняться.
При первом запросе игрового подключения backend запускает процесс один раз
на комнату, ждёт готовности и возвращает endpoint; при выходе последнего
подтверждённого игрового клиента запускается таймер простоя. Для размещённого
сайта страница по HTTPS использует `wss://`, а
reverse proxy маршрутизирует WebSocket upgrade по комнате к внутреннему
порту соответствующего процесса.

Управление процессами, пакетами и состоянием комнаты идёт через HTTP API
backend. Передача файлов пакетов идёт отдельно по HTTP; не передавать
содержимое файлов через игровые RPC.

## План реализации

### Этап 1. Проверка Godot runtime и игрового протокола

- Запустить указанный executable в headless-режиме на Windows с текущим
  проектом и параметрами `--server` / `--port`.
- Проверить результат запуска, коды завершения и вывод логов.
- Проверить WebSocketMultiplayerPeer: подключение клиента, подключение
  браузерного Godot Web export, отключение клиента и базовый RPC/сигнал.
- Для локального прототипа использовать отдельный порт на комнату:
  backend выбирает/резервирует порт, передаёт его Godot через аргументы,
  ждёт готовности сервера и возвращает браузеру локальный WebSocket endpoint.
  Проверить повторные и параллельные запросы для одной комнаты.
- Добавить минимальный прикладной handshake поверх уже установленного peer:
  соединение WebSocket само по себе ещё не делает клиента допущенным в игру;
  до подтверждения не создавать игрока и не разрешать игровые действия.
  Проверить способ передачи и проверки короткоживущего одноразового билета.
- Подготовить минимальный экспорт игры для Web. Это отдельная сборка игры,
  не текущий WASM-редактор.
- Проверить доступность игрового WebSocket-соединения из браузера с учётом
  текущего backend proxy, COOP/COEP и будущего `wss` на production.
- Зафиксировать production-направление: `wss://` за reverse proxy с
  маршрутизацией по комнате к внутреннему порту процесса. В рамках локального
  этапа не реализовывать production proxy, но не связывать игровой клиент с
  недоступными ему внутренними адресами.
- Зафиксировать точные аргументы запуска, формат адреса и ограничения
  выбранной версии Godot.

**Критерий готовности:** локальный headless-процесс Godot принимает игровой
Web-клиент через `WebSocketMultiplayerPeer` на выделенном порту, завершает
прикладное подтверждение клиента, а клиент получает хотя бы одно
подтверждаемое сервером игровое событие.

### Этап 2. Сервис жизненного цикла комнат на backend

- Реализовать в `GodotGameModule` сервис управления runtime-процессами.
- В точке запуска использовать именно `godot.windows.editor.dev.x86_64.console.exe`
  для local Windows-проверки: обычный `...editor.dev.x86_64.exe` отвязывает
  console, и backend не сможет читать `stdout`/`stderr` для readiness-check.
- Сервис должен запоминать не только комнату, но и выделенный порт и
  служебный идентификатор процесса; по `WIRED_SERVER_READY room=... port=...`
  считать запуск успешным, а по завершению/ошибке переводить процесс в
  `failed`/`stopped` и освобождать порт.
- При первом запросе игрового подключения атомарно создать ровно один
  процесс на комнату; параллельные запросы не должны запускать дубликаты.
- Ключом процесса должен быть не просто `roomId`, а пара `roomId + port`,
  чтобы избежать гонок при повторных запросах и перезапусках, а также
  поддержать повторный запуск после завершения без конфликтов портов.
- Представлять состояния процесса явно: `starting`, `running`, `stopping`,
  `stopped`, `failed`. Возвращать клиенту ошибку запуска явно, без
  успешного fallback.
- Хранить процесс и его логи, обнаруживать неожиданный выход и не считать
  комнату работающей, если процесс уже завершился.
- Проверять коды завершения: `0` — штатный выход; `2` — отсутствует
  `WIRED_GAME_TICKET_SECRET`; `3` — не удалось занять порт. Эти коды нужно
  использовать в логике backend, чтобы не считать такие сценарии
  “запуск успешен”.
- На время локального этапа хранить реестр процессов в памяти backend.
  Перезапуск backend должен корректно обнаруживать/обрабатывать оставшиеся
  процессы, либо гарантированно завершать их при выключении приложения.
- Добавить конфигурацию executable, проекта, базового порта/выделения порта
  и таймаута простоя. Не разрешать клиенту задавать произвольный executable,
  команду или путь.
- Добавить защиту от повторного использования билета и тайм-аутов handshake:
  серверный процесс должен облегчать backend, но именно backend должен
  определять, что комнаты не существует/не готова, а также не
  переиспользовать одну комнату во время `starting`.
- При присоединении игрока сбрасывать таймер простоя; при уходе последнего
  игрока запускать таймер. Учитывать потерю соединения и повторное
  подключение, не выключая комнату мгновенно.
- Завершать сервер штатной командой/сигналом остановки, позволяя Godot
  сохранить состояние; применять принудительное завершение только после
  отдельного grace period и фиксировать такую ситуацию в логах.
- В production не открывать клиенту внутренние порты; backend должен
  возвращать публичный websocket endpoint, а proxy-mapping относится к
  внутреннему порту runtime.

**Критерий готовности:** два одновременных запроса к неактивной комнате
получают один и тот же экземпляр; после ухода всех игроков и таймаута процесс
сохраняет состояние и останавливается; следующий вход запускает его снова.

### Этап 3. Подключение вкладки Game

- Добавить HTTP endpoint поверх существующего `RoomRuntimeService`: он
  проверяет существование комнаты и тип `godot`, запускает/переиспользует
  runtime через `getConnection()` и возвращает endpoint, ticket и срок его
  действия. Stage 2 реализовал сервис процессов и выдачу ticket внутри
  сервиса, но публичный контроллер/API-маршрут ещё нужно добавить.
- Входной идентификатор комнаты берётся из `room.id` (числовой ID,
  полученный после декодирования room code на frontend), а не из Hashid-кода
  ссылки. Проверять комнату на backend; не считать переданный frontend ID
  доказательством доступа.
- Защитить выдачу подключения JWT-аутентификацией через стандартный
  `UseAuthQuard()` и определить правило допуска к комнате: на первом этапе
  разрешить аутентифицированным пользователям вход в публичную Godot-комнату,
  а для приватных комнат явно проверять владельца/участника либо временно
  запрещать вход с понятной ошибкой. Не выдавать билет анонимному клиенту
  только потому, что комната доступна для чтения.
- Ограничить частоту выдачи ticket на пользователя/комнату и не позволять
  повторными запросами `getConnection()` бесконечно продлевать жизнь runtime,
  в котором нет ни одного успешно авторизованного peer. Рассмотреть
  ограниченный handshake lease/учёт выданных билетов; таймер длительного
  простоя должен основываться на подтверждённых Godot peers, а не только на
  вызовах HTTP endpoint.
- Согласовать ответ endpoint в shared API types: состояние/endpoint runtime,
  ticket и `ticketExpiresAt`. Не включать секрет `WIRED_GAME_TICKET_SECRET`
  или внутренние данные процесса. Возвращать ошибки запуска и отказа в
  доступе как явные HTTP-ошибки, не как пустой endpoint.
- Добавить API для чтения статуса runtime отдельно от join, если UI должен
  показывать статус без запуска процесса. Статусный запрос не должен сам
  запускать Godot.
- Использовать существующую browser-only схему API с авторизационным cookie;
  не полагаться на неиспользуемый server-side API-клиент.
- Заменить заглушку во вкладке Game на Godot Web export с состояниями
  загрузки экспорта, запроса runtime, handshake, готовности, ошибки и
  переподключения.
- Определить способ включения сгенерированного Web export в frontend build и
  локальный/deploy запуск: каталог `build/web` сейчас генерируется отдельно
  и не должен предполагаться уже присутствующим в репозитории. Обеспечить
  корректные MIME-типы для `.wasm`/`.pck`, COOP/COEP для потоков WASM и
  согласованные same-origin URL для экспортных ресурсов.
- Web export этапа 1 сейчас получает `ws`, `ticket` и `room` через query
  string. Для интеграции ticket в URL не переносить: передавать endpoint,
  ticket и room в игру через проверенный frontend↔Godot bridge (например,
  postMessage в same-origin iframe и JS bridge в Web export) и отправлять
  ticket только в `cli_hello`. Проверить origin/источник конфигурации и не
  сохранять credential в history, referrer или логах. Не передавать
  `WIRED_GAME_TICKET_SECRET` клиенту.
- Проверить браузерный контракт bridge отдельным сквозным тестом на том же
  origin: загрузка iframe, readiness от Godot Web, передача конфигурации,
  ticket handshake, обработка ошибки и безопасная очистка при размонтировании.
  До загрузки экспорта или при несовпадении origin не отправлять ticket.
- Одноразовый ticket расходуется сервером при успешном handshake. При
  переподключении, перезагрузке или истечении срока frontend должен запросить
  у backend новый ticket; нельзя повторно использовать credential из
  предыдущего подключения.
- Учитывать смену вкладки отдельно от фактического отключения: не
  размонтировать и не уничтожать игру при временном переключении на Editor
  или Packages. При закрытии Game/страницы корректно закрывать peer; таймер
  простоя на backend запускается только после подтверждённого ухода
  последнего игрока.
- При переподключении применять backoff и получать новый ticket на каждую
  попытку; ограничить бесконечные retries и показывать пользователю явное
  действие «повторить». Передавать backend disconnect/heartbeat только если
  это требуется фактическим протоколом; source of truth для числа игроков —
  подтверждённые Godot peers.

**Критерий готовности:** аутентифицированный пользователь с доступом к
Godot-комнате открывает вкладку Game; frontend получает одноразовый ticket
через backend, передаёт его в Web export вне URL, игровой клиент успешно
проходит handshake и получает серверное событие. Ошибка запуска, отказ в
доступе, просроченный/использованный ticket и потеря связи показываются
явно; повторное подключение получает новый ticket, а переключение на другую
вкладку не закрывает игру. Экспорт загружается с корректными MIME и
COOP/COEP-заголовками, не требует ручного копирования неотслеживаемого
артефакта для обычного локального запуска.

### Этап 4. Хранение пакетов и пофайловая загрузка

- Зафиксировать модель: в Godot-проекте комнаты может быть несколько папок
  пакетов; каждая папка соответствует отдельному `ScriptingPackage`/ID на
  backend. Пакет — не вся папка комнаты и не синоним комнаты. Имена, состав
  файлов и ревизии одного пакета не должны затрагивать соседние пакеты.
- Согласовать минимальный формат пакета: идентификатор, имя, ревизия,
  перечень относительных путей, размеры и криптографические хеши файлов.
- Определить каталоги и правила размещения пакетов внутри файловой системы
  Godot-проекта, например `res://packages/<packageId>/`. Для открытого
  редактора этот каталог — источник черновых файлов: перед Emit frontend
  читает файлы только выбранной папки пакета из Godot FS, а не пытается
  получить их из файловой системы браузера или из backend.
- Интегрироваться с FS кастомной WASM-сборки через экземпляр редактора
  (`window.editor.editor.rtenv.FS`). Обернуть чтение и запись в типизированный
  frontend bridge с проверкой готовности редактора и понятной обработкой
  отсутствующих путей/ошибок FS; не распространять прямые обращения к
  глобальному `window.editor` по UI-компонентам.
- Проверить API и семантику `rtenv.FS` именно в используемой кастомной
  сборке Godot: чтение, создание каталогов, запись и обновление файлов,
  видимость изменений редактору и сохранение после перезапуска. Учитывать,
  что вызов FS не равнозначен изменению исходника на диске сервера.
- Сохранять физические файлы отдельно в файловом хранилище backend; выдавать
  их по существующим/расширенным endpoints. Метаданные Postgres должны
  отражать опубликованную ревизию и состав файлов.
- Валидировать относительные пути и запрещать выход из каталога пакета,
  абсолютные пути и неоднозначные дубликаты путей.
- Разделить черновик и опубликованную ревизию: частичная загрузка или сбой
  не должны заменять последнюю корректную опубликованную версию.
- Добавить в Godot-проект загрузчик пакетов, который получает манифест,
  скачивает нужные файлы, сверяет хеши и применяет их в отдельный каталог
  runtime-копии выбранного пакета. Не считать runtime-кэш под `user://`
  исходной папкой проекта редактора; подтвердить поддерживаемый Godot способ
  динамической загрузки ресурсов из этого каталога.
- После публикации frontend получает событие о новой ревизии, загружает
  файлы по HTTP, проверяет манифест/хеши и записывает содержимое в каталог
  соответствующего пакета (`packages/<packageId>/`) через Godot FS. Редактор
  должен увидеть
  синхронизированные файлы без перезагрузки всей страницы; проверить,
  требуется ли для перечитывания файлов обновить файловую систему Godot или
  перезапустить/переоткрыть проект редактора.
- Продумать правила замены/удаления файлов между ревизиями: отсутствующие
  в новой ревизии файлы должны удаляться только из управляемого каталога
  пакета, никогда — произвольные файлы проекта.

**Критерий готовности:** пакет из нескольких файлов можно загрузить,
проверить хеши, опубликовать и получить на сервере и клиенте без архива и без
изменения файлов вне каталога пакета.

### Этап 5. Emit и согласованное применение ревизии

- Использовать существующий `POST /scripting-packages/:id/revisions/:rev/publish`
  как операцию Emit: он уже проверяет загруженные файлы и хеши и фиксирует
  неизменяемую опубликованную ревизию. Не добавлять второй endpoint с тем же
  назначением. Считать `published` подтверждением фиксации на backend, а не
  подтверждением применения ревизии runtime или редактора.
- Событие `ScriptingPackageRevisionPublishedEvent`, которое сейчас испускается
  после публикации, — только локальный сигнал NestJS для запуска диспетчеризации,
  не транспорт и не гарантия доставки. Передавать runtime уведомление через
  отдельный контрольный канал/протокол; не смешивать этот канал с игровым
  `WebSocketMultiplayerPeer` и не подменять им HTTP-загрузку файлов.
- Уведомление должно содержать идентификаторы пакета и ревизии, а не байты
  файлов. Получатель скачивает манифест и файлы через существующие HTTP
  endpoints и повторно проверяет хеши. Диспетчеризация и применение должны
  быть идемпотентны для пары room/package/revision; определить явные состояния
  «опубликовано», «применено сервером», «готово на клиентах» и ошибку/отставание
  отдельной цели. Сбой отдельного клиента не должен отменять уже опубликованную
  ревизию или скрываться под общим статусом успеха.
- Уведомление может быть потеряно при перезапуске backend/runtime. Считать
  его сигналом к синхронизации, а манифест — источником истины: при старте и
  переподключении runtime, а также при повторном открытии редактора получать
  актуальный манифест и сверять ревизии; предусмотреть повторную попытку
  диспетчеризации/синхронизации и наблюдаемый статус ошибок. Не обещать
  гарантированную доставку только на основании in-memory EventEmitter.
- Разрешать целевую комнату по привязке конкретного пакета
  (`ScriptingPackage.room`); одна комната может иметь и синхронизировать
  несколько package ID независимо. Явно решить, как обрабатываются пакеты
  без комнаты и дочерние/общие пакеты. Не рассылать обновление всем комнатам
  только по факту наличия package ID.
- Godot-сервер сначала скачивает и проверяет ревизию, затем подтверждает её
  применение и уведомляет подключённых игровых клиентов об идентификаторе
  версии. Клиенты скачивают файлы по HTTP, проверяют их и сообщают готовность;
  сервер должен явно учитывать клиентов, которые ещё загружают файлы или
  завершили синхронизацию с ошибкой. До реализации определить по результатам
  прототипа Stage 1/4, какие типы ресурсов действительно можно применять
  без перезапуска; для остальных ограничить первую версию или определить
  контролируемый перезапуск.
- Подключённые вкладки Editor получают уведомление через канал событий
  backend (например, WebSocket/SSE) или контролируемый опрос. Frontend
  скачивает новую опубликованную ревизию и обновляет пакетные файлы в Godot
  FS. Следует определить поведение при локальных несохранённых изменениях:
  не перезаписывать их молча; явно показать конфликт и предложить сохранить,
  сравнить или заменить содержимое.
- Согласовать поведение при ошибках: не сообщать об успешном Emit, если
  файлы не зафиксированы; не считать синхронизацию завершённой, пока сервер
  и целевые редакторы не применили версию; показывать отдельный статус
  клиентам/редакторам, которые ещё загружают или не смогли применить пакет.
- Обеспечить повторную загрузку актуального манифеста при входе нового
  клиента или открытии редактора, чтобы игра и редактор получили текущие
  пакеты, даже если пропустили уведомление.

**Критерий готовности:** после Emit backend возвращает опубликованную ревизию
только после проверки и фиксации файлов; runtime и активные клиенты получают
один идентификатор ревизии и показывают отдельные статусы применения/ошибок.
Открытые редакторы получают файлы в виртуальную FS без молчаливой потери
локальных изменений; runtime, клиент или редактор, пропустивший уведомление,
при повторном подключении/открытии сверяет манифест и догоняет последнюю
опубликованную ревизию.

### Этап 6. Интерфейс Packages и сквозные проверки

**Решения по поведению редактора (2026-10-30).** Редактор — инструмент
редактирования контента, а не игровой клиент. Поэтому синхронизация пакетов
в редактор и в игру разделяется:

- Пакеты попадают в редактор только по явному действию пользователя.
  Автоматическая запись опубликованных пакетов в FS при старте редактора из
  этапа 5 отменяется.
- После перезагрузки страницы редактор открывается пустым: набор загруженных
  пакетов не сохраняется и не восстанавливается автоматически.
- Панель Packages показывает все пакеты комнаты и их состояние: «не загружен»,
  «загружен», «есть новая ревизия», «локальные изменения/конфликт».
- «Скачать в редактор» скачивает выбранный пакет, проверяет манифест и хеши и
  записывает файлы в `packages/<packageId>/` через Godot FS. «Убрать из
  редактора» удаляет только каталог этого пакета.
- Только что созданный пакет сразу создаётся в FS пустым каталогом, чтобы
  пользователь мог добавлять в него файлы. Остальные пакеты комнаты при
  создании не загружаются.
- Emit доступен только для пакета, загруженного в редактор: frontend читает
  его каталог из FS, создаёт черновик, загружает файлы и публикует ревизию.
  После Emit серверный процесс и все Game-клиенты обновляются автоматически;
  редакторы других пользователей не меняются, у них в панели появляется
  отметка о новой ревизии и кнопка загрузить её.
- Перед реализацией проверить в используемой сборке Godot, видит ли уже
  запущенный редактор файлы, записанные напрямую в `rtenv.FS`, как обычную
  ФС, без перезапуска и пересканирования. Если видит — «Скачать в редактор»
  применяет файлы сразу; если нет — показать явное требование перезапустить
  или переоткрыть проект. Результат проверки зафиксировать в спеке этапа 6.
- Удаление пакета с локальными изменениями и замена загруженного пакета новой
  ревизией: на этом этапе достаточно явного подтверждения пользователя;
  полноценное сравнение файлов не требуется.
- В дальнейшем добавить владение/блокировку пакетов: каждый пользователь
  сможет делать Emit только для своего пакета. Многопользовательское
  редактирование одного пакета в этап 6 не входит.

Реализация:

- Восстановить список пакетов и создание пакета в панели Packages.
- Связать Packages с текущей комнатой и открытым экземпляром редактора:
  показывать несколько пакетов комнаты; создание каждого пакета формирует
  отдельный каталог `packages/<packageId>/` в Godot FS, а сохранение и Emit
  работают только с выбранным каталогом и отправляют его файлы на backend.
- При загрузке комнаты перечислять все связанные с ней пакеты, но не
  синхронизировать их в FS автоматически. Не предполагать единственный пакет
  на комнату и не перезаписывать каталоги соседних пакетов при создании,
  Emit, загрузке, удалении или применении.
- Добавить явные действия «Скачать в редактор» и «Убрать из редактора» для
  каждого пакета, а также статус «есть новая ревизия» по данным
  `GET /rooms/:roomId/game/packages`; внешние обновления не записываются в FS
  без действия пользователя.
- Добавить явную кнопку Emit, состояния публикации и ошибок загрузки/
  применения.
- Проверить сценарии: пустой редактор после перезагрузки; создание пакета и
  появление его каталога; скачивание и удаление отдельного пакета; Emit
  выбранного пакета; два клиента; Emit во время игры (Game-клиенты и runtime
  обновляются, редактор другого пользователя — нет); появление отметки о новой
  ревизии и её загрузка в редактор; видимость записанных в FS файлов без
  перезапуска; позднее подключение клиента и повторное открытие редактора;
  потеря сети и повторное подключение; конфликт локальных и опубликованных
  файлов; неудачная публикация; остановка по простою; восстановление
  сохранённой сцены.
- Добавить unit-тесты управления процессом и API пакетов, а также ручной
  сквозной checklist для локальной Windows-разработки.

## Будущее направление: marketplace пакетов (после этапа 6)

Зафиксировано 2026-10-30. Не входит в этап 6; учитывать при планировании
следующих этапов.

- Пакеты комнаты («room packages») и глобальный marketplace — разные
  пространства. Room-пакет привязан к комнате, его опубликованные ревизии
  получают runtime и Game-клиенты этой комнаты. Marketplace-пакет не привязан
  к комнате и доступен как глобальный контент Wired.
- Публикация в комнату (Emit) и публикация в marketplace — две разные
  операции. Emit публикует ревизию room-пакета. Публикация в marketplace
  делает пакет доступным в глобальном каталоге; сама по себе она не запускает
  обновление runtime или комнат.
- В панели Packages появятся отдельные разделы «Room packages» и
  «Marketplace».
- Пакет, созданный пользователем, но ещё не Emit-нутый, виден только автору
  на его странице. После первого Emit он становится room-пакетом комнаты и
  виден всем, у кого есть доступ к комнате.
- Добавление marketplace-пакета в комнату создаёт копию/форк: новый
  room-пакет со своим ID, привязкой к комнате и независимой историей ревизий.
  Это не ссылка: последующие изменения marketplace-пакета не попадают в
  комнату, а изменения room-копии не меняют оригинал.
- При копировании нужно решить: переносить только последнюю опубликованную
  ревизию как первую ревизию копии или всю историю; как фиксировать
  происхождение (существующие `parentPackage`/`childrenPackages` или отдельное
  поле); кто становится владельцем копии. Решение принять при планировании
  marketplace.
- Публикация в marketplace и добавление в комнату должны идти через backend
  API с проверкой авторства и доступа к комнате. Будущая блокировка Emit по
  владельцу пакета описана в этапе 6; здесь она должна учитываться так же.
- Схему БД не менять до отдельного согласования: действуют `DB_SYNC=1` и
  общая база, изменения затрагивают существующие данные.

## Нерешённые технические вопросы для прототипа

1. Как доставлять команды в уже запущенный headless-процесс: отдельное
   контрольное соединение с backend или предусмотренный Godot сетевой
   протокол. Выбрать после проверки минимального Godot прототипа.
2. Как реализовать прикладную аутентификацию игрового соединения. Нельзя
   полагаться на произвольный HTTP Authorization header: браузерный WebSocket
   API ограничивает пользовательскую настройку заголовков. Проверить
   одноразовый короткоживущий билет в первом прикладном сообщении либо иной
   безопасный способ, поддерживаемый используемой кастомной сборкой. До
   успешной проверки сервер не должен допускать peer к игровым RPC и
   состоянию комнаты.
3. Какие типы ресурсов действительно можно динамически подключать из
   скачанных отдельных файлов как в Web export, так и в headless-сборке.
   Проверить сцены, скрипты, текстуры и зависимости на поддерживаемой версии
   Godot. Если некоторые типы нельзя подключать без перезапуска, определить
   ограничение первой версии и безопасную процедуру перезагрузки.
4. Как Godot-проект будет запрашивать файлы у backend: подписанные URL,
   credential runtime или локальный доверенный endpoint. Клиент не должен
   получать полномочия на запись или публикацию пакетов.
5. Как игра сохраняет и восстанавливает состояние сцены, и как определять
   активность runtime: подтверждённые игровые peers, heartbeat или оба
   сигнала. Открытая вкладка Editor без игрового подключения сама по себе
   серверный процесс не удерживает; при необходимости это решение можно
   пересмотреть отдельно.
6. Видит ли уже запущенный Godot-редактор файлы, записанные напрямую в
   `rtenv.FS` через Emscripten, как обычную файловую систему, без перезапуска
   и пересканирования проекта. Проверить в этапе 6; от результата зависит,
   можно ли применять скачанный пакет в открытый редактор сразу или нужно
   явно требовать перезапуск.

## Ограничения и границы безопасности

- Текущий файловый API пакетов требует проверки нормализации путей и прав
  доступа до использования для игровых ресурсов.
- Исполняемые скрипты и ресурсы пользовательских пакетов потенциально
  недоверенные. Локальный режим не является границей безопасности для
  публичного запуска; перед production нужны изоляция процессов, ограничения
  ресурсов, строгие разрешения и аутентификация клиентов.
- Не запускать пользовательские команды из данных пакета. Команда процесса
  Godot и пути к проектам задаются только серверной конфигурацией.
- Перед изменениями Entity/схемы учитывать текущую настройку `DB_SYNC=1` и
  влияние на общую базу. Новые поля/таблицы сначала согласовать и проверить
  на сохранность существующих данных.

## Локальная конфигурация

Первоначально поддержать конфигурационные значения, например:

- `GODOT_RUNTIME_PATH` — путь к Godot executable;
- `GODOT_RUNTIME_PROJECT_PATH` — проект для серверного процесса;
- `GODOT_ROOM_PORT_START` / `GODOT_ROOM_PORT_END` — диапазон локальных
  портов, резервируемых backend для отдельных серверных процессов комнат;
- `GODOT_ROOM_IDLE_TIMEOUT_MS` — время до остановки неактивного процесса;
- `GODOT_ROOM_SHUTDOWN_GRACE_MS` — время на сохранение и штатное завершение.

Имена и значения окончательно определить по существующему конфигурационному
стилю и результатам этапа 1. Локальные абсолютные пути не коммитить в код и
не выводить из `.env` в отчёты.

## Порядок начала реализации

Начать с **этапа 1**: проверить `WebSocketMultiplayerPeer` между headless
сервером и Web export через локальный выделенный порт, handshake игрового
клиента и отдельную Godot FS кастомной сборки (чтение/запись файлов пакета,
уведомление редактора о внешнем изменении, необходимость повторного
импорта). Пока не менять существующий CRUD, схему БД и UI. По результатам
прототипа уточнить способ контрольных команд, прикладную аутентификацию,
динамическое подключение типов файлов в Web export и механизм обновления
открытого редактора. После этого реализовывать этапы 2–6 небольшими
проверяемыми изменениями.
