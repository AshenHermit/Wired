# Локализация фронтенда: next-intl, язык в cookie

Дата: 2026-11-03
Статус: proposal

## 1. Интент

Сейчас весь текст интерфейса зашит в компоненты и модули фронтенда по-русски:
19 исходных файлов, 319 строк с кириллицей (без тестов), плюс 10 тестовых
файлов, которые проверяют русские подписи. Язык нельзя сменить, строки нельзя
перевести, а `<html lang>` в корневом layout стоит `en` — то есть разметка
врёт о языке содержимого.

Задача: вынести пользовательские строки в отдельные файлы сообщений и
подключить `next-intl`. Язык хранится в cookie (`NEXT_LOCALE`), по умолчанию —
английский (`en`), второй язык — русский (`ru`). URL и существующие ссылки
`/room/<hashid>` не меняются. У пользователя появляется переключатель языка,
доступный и гостям (в том числе на странице логина).

Настройка в сущности `User` не делается: в ходе обсуждения выбрано хранение в
cookie, чтобы не менять БД и API и чтобы язык работал до авторизации.

## 2. Goals

- `next-intl@4.14.9` подключён к `frontend/` без locale-роутинга.
- Каталоги `frontend/messages/en.json` и `frontend/messages/ru.json`; `en` —
  источник истины и язык по умолчанию.
- Все пользовательские строки фронтенда (подписи, placeholder'ы, aria-label,
  тосты, ошибки и статусы, видимые в UI) берутся из каталогов.
- Язык читается на сервере из cookie `NEXT_LOCALE`; первый рендер сразу на
  выбранном языке, без вспышки другого языка.
- `<html lang>` соответствует локали.
- Переключатель языка виден на главной/логине и в комнате; выбор сохраняется
  между перезагрузками и не зависит от аккаунта.
- Существующие URL, включая `/room/<hashid>`, остаются прежними.
- Тесты продолжают проходить; добавляются проверки паритета каталогов и
  переключателя.

## 3. Non-goals

- Поле языка в `User`, миграции, изменения `PATCH /users/:id` и `packages/shared`.
- Locale-префиксы (`/en/...`, `/ru/...`), сегмент `[locale]`, middleware/proxy.
- Автоопределение языка по `Accept-Language` или геолокации: только cookie,
  иначе `en`.
- Перевод текста внутри Godot-редактора и игры (iframe/WebGL) — это не наш UI.
- Перевод серверных ошибок NestJS и сообщений API: фронтенд показывает свои
  формулировки по коду ошибки, а не сырой `message` сервера.
- Перевод комментариев в коде, `console.*`, имён пакетов, slug'ов, HTTP-кодов.
- Платформа переводов (Crowdin и т.п.) и автогенерация ключей.
- Локализация метаданных (`title`/`description`) и OG-тегов.

## 4. Anti-goals

- Оставить в компонентах пользовательские строки «на потом».
- Сломать или переименовать существующие ссылки на комнаты.
- Показывать английскому пользователю русские технические сообщения
  (`Мост редактора недоступен`, `staging не найден` и т.п.).
- Дублировать каталоги с расходящимся набором ключей.
- Городить второй механизм переводов рядом с next-intl (свой словарь,
  `useContext` с текстом и т.п.).
- Тянуть locale-роутинг ради двух языков без локализованных URL.

## 5. Constraints

- `next@16.0.7`, React 19.2, App Router, сборка через `next build --webpack`
  (не менять на Turbopack). `next-intl@4.14.9` объявляет peer support Next 16.
- Почти весь UI — клиентские компоненты (`"use client"`); серверный только
  корневой `src/app/layout.tsx` и тонкие `page.tsx`-обёртки.
- COOP/COEP-заголовки заданы на `/:path*` в `next.config.ts`; locale-механика
  не должна требовать middleware или менять эти заголовки.
- Ссылки на комнаты кодируются Hashids и уже раздаются пользователям;
  префикс локали их бы сломал.
- Vitest 5 + jsdom, `vitest.config.mts`; компоненты с `useTranslations` без
  провайдера падают, поэтому тестам нужна обёртка.
- `packages/shared` не трогаем: фронтенд использует только `User`/`Room` и др.
- `pnpm` workspace; зависимость добавляется только в `frontend/package.json`.
- Текущий UI по-русски, включая неформальный тон на главной; английский текст
  должен передавать смысл, а не быть дословным.

## 6. Approaches

| Вариант | Что даёт | Чем платим |
|---|---|---|
| **A. Cookie + серверный layout** (выбрано) | Первый рендер сразу на нужном языке, ноль изменений URL и роутинга, минимум кода | Корневой layout становится динамическим; смена языка — `router.refresh()` |
| B. Cookie + server action | Cookie ставится на сервере, «правильнее» по Next.js | Лишний файл, сетевая операция на клик, выигрыша нет |
| C. `[locale]` в роутинге next-intl | Локализованные ссылки, готовые `Link`/`redirect` | Меняет структуру `app/` и/или URL, ломает существующие ссылки на комнаты |

Выбран A: он решает задачу (язык в cookie, дефолт `en`, ссылки не меняются) с
наименьшим объёмом изменений. B не даёт преимуществ: приложение и так
клиентское, а server action не отменяет `router.refresh()`. C противоречит
anti-goal про стабильные URL.

## 7. Design

### 7.1. Подключение next-intl

Новые файлы:

```
frontend/
├── messages/
│   ├── en.json
│   └── ru.json
├── global.d.ts
└── src/i18n/
    ├── config.ts
    └── request.ts
```

- `frontend/package.json`: `"next-intl": "^4.14.9"`.
- `src/i18n/config.ts`:
  ```ts
  export const locales = ["en", "ru"] as const;
  export type Locale = (typeof locales)[number];
  export const defaultLocale: Locale = "en";
  export const LOCALE_COOKIE = "NEXT_LOCALE";
  export function isLocale(value: string | undefined): value is Locale;
  ```
- `src/i18n/request.ts`:
  ```ts
  export default getRequestConfig(async () => {
    const store = await cookies();
    const cookieLocale = store.get(LOCALE_COOKIE)?.value;
    const locale = isLocale(cookieLocale) ? cookieLocale : defaultLocale;
    return {
      locale,
      messages: (await import(`../../messages/${locale}.json`)).default,
    };
  });
  ```
  Некорректное/отсутствующее значение cookie → `en`, без исключения.
- `next.config.ts`: обернуть конфиг в `createNextIntlPlugin()`:
  ```ts
  const withNextIntl = createNextIntlPlugin();
  export default withNextIntl(nextConfig);
  ```
  Существующие `headers()` и `rewrites()` остаются как есть.
- `frontend/global.d.ts`: type augmentation по документации v4:
  ```ts
  import messages from "./messages/en.json";
  declare module "next-intl" {
    interface AppConfig {
      Locale: (typeof locales)[number];
      Messages: typeof messages;
    }
  }
  ```
  Это даёт автодополнение и проверку ключей в `t("...")`. Каталог `ru`
  обязан повторять набор ключей `en` (проверяется тестом, см. §7.6).
- `src/app/layout.tsx` становится `async`:
  ```tsx
  const locale = await getLocale();
  const messages = await getMessages();
  return (
    <html lang={locale}>
      <body ...>
        <NextIntlClientProvider locale={locale} messages={messages}>
          <UserProvider />
          {children}
          <Toaster />
        </NextIntlClientProvider>
      </body>
    </html>
  );
  ```
  `Toaster` остаётся внутри провайдера: тексты тостов формируются в вызывающем
  коде через `t`, сам `Toaster` строк не содержит. Метаданные не меняются.

Следствие: чтение cookie делает дерево динамическим (SSR на каждый запрос).
Для приложения с авторизацией и комнатами это уже фактически так; статическая
генерация главной не является требованием.

### 7.2. Хранение и переключение языка

- Cookie: имя `NEXT_LOCALE` (конвенция next-intl), `Path=/`,
  `Max-Age=31536000`, `SameSite=Lax`; `Secure` добавляется, если
  `location.protocol === "https:"`. Cookie не `HttpOnly` — её ставит клиент.
- Компонент `src/components/i18n/LocaleSwitcher.tsx` (`"use client"`):
  - `useLocale()` и `useRouter()` из `next/navigation`;
  - варианты `en` / `ru`, подписи «English» / «Русский»;
  - при выборе: записать cookie, затем `router.refresh()` внутри
    `startTransition`; на время перехода элемент disabled;
  - `aria-label` из каталога (`Common.language`).
- Смена языка не вызывает навигацию и не меняет URL; `router.refresh()`
  перерисовывает серверные части и обновляет `NextIntlClientProvider`.
- Точки монтирования:
  - `src/app/(browser)/layout.tsx` — компактный переключатель в правом верхнем
    углу, виден на главной и логине (включая гостей);
  - `src/app/room/[room_code]/(godot)/RoomPageClient.tsx` — компактный вариант
    в существующей плавающей панели вкладок, рядом с `TabsList`;
  - `src/app/room/[room_code]/page-client.tsx` — в экранах «комната
    недоступна» и «ts-game не поддерживается», чтобы язык можно было сменить
    даже на ошибке.
- Стиль: существующие `Button`/`RippleButton` и `Tabs`-примитивы; отдельный
  компонент не тащит новых зависимостей.

### 7.3. Структура сообщений

Один namespace на область, ключи семантические (не по тексту). Верхний уровень:

| Namespace | Содержимое |
|---|---|
| `Common` | Сохранить, Отмена, Повторить, Удалить, Загружаем…, язык |
| `Home` | вкладки, заголовки, приветствие, тексты карточки |
| `Login` | заголовок и подписи формы входа |
| `Profile` | диалог редактирования профиля (сейчас английский текст в коде) |
| `Rooms` | список, создание/редактирование/удаление, пустые состояния |
| `Workshop` | каталог, поиск, карточки, диалоги публикации/fork |
| `Packages` | панель пакетов, статусы, диалоги, действия, уведомления |
| `Tags` | поле тегов, подсказки, ошибки, plural для количества |
| `Slug` | подсказки валидации slug |
| `Room` | оболочка комнаты, вкладки Editor/Packages/Game, ошибки загрузки |
| `Game` | статусы запуска, ошибки подключения, «Игроков: N» |
| `Editor` | статусы и ошибки запуска Godot-редактора |
| `Errors` | общие ошибки запросов, моста, файловой системы, runtime |

Правила:
- Интерполяция — ICU (`{name}`, `{count}`), плюрализация — ICU plural
  (`{count, plural, one {# пакет} few {# пакета} many {# пакетов} other {…}}`).
  Ручная функция `pluralizePackages` в `tag-input.tsx` удаляется.
- Строки с разметкой (`<strong>`, `<span>`) переводятся через `t.rich` с
  React-узлами; в JSON хранится разметка в допустимом для next-intl виде.
- Кавычки и спецсимволы экранируются по правилам ICU; фигурные скобки в
  тексте удваиваются.
- Пользовательские значения (имя пакета, slug, имя файла, HTTP-статус) — только
  через переменные, не склеиваются в переводимый текст.
- Комментарии в коде не переводятся и не выносятся.

### 7.5. Строки вне React

Часть сообщений рождается в обычных модулях (классы ошибок, hook'и, файловая
система) и затем показывается в UI. Правило:

- Модуль не хранит готовый пользовательский текст. Вместо этого — типизированный
  код ошибки и значения: `AppError`/`EditorBridgeError` с
  `code` (ключ из `Errors`) и `values`.
- `message` у ошибок остаётся диагностическим (для логов и тестов); в UI он не
  выводится.
- Перевод происходит на границе отображения: компоненты вызывают
  `useTranslations`; hook'и (`use-room-packages`, `use-editor-bridge`) отдают
  коды/ключи, а не готовый текст (см. §7.5.1). `onConnectError` принимает
  `{ key, values }` вместо строки.
- Неизвестная ошибка показывается общей переведённой формулировкой
  (`Errors.unexpected`); исходный `message` уходит в `console.error`.
- Тосты (`toast.success/error`) переводятся в месте вызова.
- Низкоуровневые сообщения `editor-bridge.ts` и `godot-packages-fs.ts`
  (таймауты, «staging не найден») остаются диагностикой и не попадают в UI
  как есть: их показывают переведённые сообщения по коду/контексту.

Это позволяет не тащить React-контекст в чистые модули и не превращать
`Error.message` в ключ перевода.

#### 7.5.1. Состояние, живущее дольше одного рендера

Строки нельзя вычислять через `t` в момент события и класть готовый текст в
state: после смены языка `router.refresh()` перерисует оболочку, а сохранённый
текст останется на старом языке. Поэтому:

- `GameTab` хранит в reducer'е не `message: string`, а
  `message: { key: GameMessageKey; values?: Record<string, string | number> }`
  (или эквивалентный discriminated union). Текст собирается в компоненте при
  рендере через `t(key, values)`.
- `use-room-packages` хранит в `action.notice` / `action.error` / `state.error`
  ключ и значения; toast/уведомление формируются в компоненте или в
  hook'е-потребителе, который уже имеет доступ к `useTranslations`.
- `GameTab` дополнительно хранит коды статусов (`status`, `code`), а не готовые
  подписи; `statusLabel(code)` остаётся функцией, возвращающей ключ.
- Смена языка не требует перезапуска игры: текст статусов пересчитывается из
  state при следующем рендере, iframe не размонтируется.
- Правило распространяется на любые reducer'ы/store'ы, где сейчас лежит
  пользовательский текст. Чистые данные (имена, slug'и, файлы) остаются
  значениями.

Это осознанно увеличивает объём работ по `GameTab` и `use-room-packages`, зато
переключение языка даёт полностью переведённый экран, а не смесь языков.

#### 7.5.2. Текст из внешних источников

Два места получают текст, который фронтенд не формирует:

- сообщения игрового iframe (`data.payload.message`, `data.payload.detail`
  в `GameTab`);
- `entry.runtimeError` с бэкенда в `PackagesTab`.

Решение: показывать их как есть, без перевода и без подмены общей ошибкой.
Язык такого текста зависит от игры/сервера, но это единственная диагностика
при падении runtime; терять её нельзя. Оболочка вокруг (заголовки, кнопка
«Повторить», общий статус) остаётся переведённой. Это единственное
запланированное исключение из правила «в UI нет сырых сообщений».

#### 7.5.3. Ошибки API без кода

`useRequestHandler` перестаёт показывать `error.message` как есть. Вместо этого:

- известные доменные коды (`package_not_published`, `slug_taken`,
  `invalid_tags`, …) маппятся на конкретные ключи `Errors.*`;
- для остальных HTTP-ошибок — карта по статусу: `401`/`403` (нет доступа),
  `404` (не найдено), `409` (конфликт), `5xx` (сервер), всё прочее —
  `Errors.unexpected`;
- операции с комнатами (создание/изменение/удаление) получают явные ключи
  `Rooms.errors.*`, чтобы вместо «что-то пошло не так» было понятное действие;
- исходный `message` и статус уходят в `console.error`. Серверные сообщения не
  переводятся (non-goal).

### 7.6. Тесты

- Новый helper `src/test/render-with-intl.tsx`:
  ```tsx
  export function renderWithIntl(ui, { locale = "ru" } = {}) {
    return render(
      <NextIntlClientProvider locale={locale} messages={messages[locale]}>
        {ui}
      </NextIntlClientProvider>,
    );
  }
  ```
  Каталоги импортируются статически (`messages/en.json`, `messages/ru.json`).
- Тесты, рендерящие переведённые компоненты (10 файлов, включая `GameTab`,
  `PackagesTab`, `workshop-browser`, `tag-input`, `use-room-packages`,
  `GodotEditor`), переводятся на `renderWithIntl` с `locale: "ru"` по
  умолчанию — существующие проверки русского текста остаются валидными и
  проверяют русский каталог.
- Новые тесты:
  - паритет каталогов: одинаковый набор ключей в `en` и `ru` (рекурсивно) и
    одинаковый набор ICU-переменных в каждом сообщении;
  - `LocaleSwitcher`: выбор `ru` пишет `document.cookie` с `NEXT_LOCALE=ru` и
    вызывает `router.refresh()` (mock `next/navigation`);
  - рендер с `locale: "en"` даёт английские подписи (например, вкладки
    главной) — фиксирует дефолтный язык;
  - смена языка перерисовывает уже показанный статус: `GameTab` с сохранённым
    состоянием («Игра недоступна» + сообщение) рендерится в провайдере `ru`,
    затем тот же компонент — в провайдере `en`; текст статуса меняется без
    изменения state. Аналогичная проверка для `action.notice` в
    `use-room-packages`.
- Тесты `GameTab`/`use-room-packages`, которые сейчас сравнивают готовые
  строки, продолжают работать через `renderWithIntl("ru")`: компонент сам
  переводит ключи из state.
- Чистые тесты `editor-bridge.test.ts` и `godot-packages-fs.test.ts` не
  оборачиваются: они проверяют диагностические сообщения, а не UI.
- `pnpm --filter frontend test` должен остаться зелёным; число тестов растёт.

Дополнительно: `vitest.config.mts` не требует изменений, пока не используется
`createNavigation`. Если ESM-импорт `next-intl` в Vitest упадёт, добавить
`test.server.deps.inline: ["next-intl"]` по документации.

### 7.7. Детали и краевые случаи

- Cookie невалидна/отсутствует → `en`; `ru` выбирается только явно.
- Первый визит гостя → английский интерфейс; переключатель доступен сразу на
  логине.
- `router.refresh()` сохраняет текущий путь, включая `/room/<code>`; вкладки
  комнаты и смонтированный iframe не размонтируются, потому что навигации нет.
- Смена языка во время работы игры не перезапускает Godot-рантайм: текст
  оболочки обновляется, содержимое iframe — нет.
- `html lang` меняется вместе с локалью; гидратация не должна ругаться, так
  как язык приходит с сервера и на клиенте не пересчитывается.
- NextIntlClientProvider получает полный каталог (не только использованные
  namespace). Для двух языков и текущего объёма текста это приемлемо; при
  росте каталога можно перейти на клиентскую загрузку namespace.
- Тексты в `metadata` и `alt="logo"` не переводятся (non-goal); `alt` логотипа
  можно оставить как есть.
- Строки в `title`/`aria-label` кнопок-иконок (перетаскивание панели, очистка
  поиска, действия с пакетом) входят в каталоги.

## 8. Порядок работ (крупными срезами)

1. Инфраструктура: зависимость, plugin, `i18n/config.ts`, `i18n/request.ts`,
   `global.d.ts`, async layout, пустые каталоги, `LocaleSwitcher` и его
   монтирование.
2. `Common`, `Home`, `Login`, `Profile`, `Rooms` + `slug.ts`/`use-request-handler`
   (включая маппинг API-ошибок по статусу).
3. Состояние: `GameTab` reducer и `use-room-packages` переходят на ключи и
   параметры; тесты подтверждают смену языка без повторного события.
4. `Workshop`, `Tags`, `Packages` (панель, диалоги), `Room`, `Editor`, `Game`,
   низкоуровневые ошибки моста/ФС.
5. Тестовый helper, миграция тестов, новые тесты, проверки типов/линта/сборки.

Каждый срез оставляет приложение рабочим; промежуточное состояние с
непереведёнными строками допустимо только внутри одной ветки, не в main.

## 9. Verification

- `pnpm --filter frontend test` — все suites зелёные, включая новые.
- `pnpm check-types:frontend` — типы ключей сообщений и `AppConfig` сходятся.
- `pnpm --filter frontend lint`.
- `pnpm --filter frontend build` — `createNextIntlPlugin` работает с webpack.
- Ручная проверка:
  - чистый профиль браузера → главная и логин на английском, `<html lang="en">`;
  - переключение на русский → текст сразу меняется, после F5 остаётся русским,
    cookie `NEXT_LOCALE=ru`;
  - переключение языка при уже показанном статусе игры или уведомлении пакета →
    этот текст тоже меняется сразу, без повторного события и без перезапуска
    iframe;
  - сообщение из игрового iframe и `runtimeError` остаются на языке источника
    (осознанное исключение);
  - переход по существующей ссылке `/room/<hashid>` не меняет URL и не ломает
    Hashids;
  - в комнате переключатель доступен, вкладки/iframe не перезапускаются;
  - в каталогах нет ключей, отсутствующих во втором языке.

## 10. Решения, принятые при обсуждении

- Языки: `en` (по умолчанию) и `ru`. Третий язык не запрошен; добавление —
  новый файл каталога и одна строка в `locales`.
- Хранение: cookie, не поле пользователя (явно изменено в ходе обсуждения).
- URL: без locale-префикса; ссылки на комнаты сохраняются.
- Переключатель: в шапке `(browser)`-layout и в панели комнаты; гостям доступен.
- Тесты по умолчанию рендерят русский каталог, чтобы не переписывать сотни
  существующих проверок; английский покрывается отдельными тестами.
- Диагностические сообщения низкоуровневых модулей не переводятся и в UI не
  показываются.
- Смена языка обязана переводить и уже показанные статусы/уведомления, поэтому
  `GameTab` и `use-room-packages` хранят ключи и параметры, а не готовый текст.
- Текст из игрового iframe и `entry.runtimeError` показываются как есть — это
  внешняя диагностика, её язык не наш.
- Ошибки API без доменного кода маппятся по HTTP-статусу; у операций с
  комнатами есть собственные ключи.
- Существующий русский текст переносится дословно (включая опечатки); английский
  переводится по смыслу. Правка русских формулировок — отдельная задача и
  отдельный diff тестов.
- `sr-only "Close"` в registry-компонентах `animate-ui` входит в `Common`.

## 11. Риски

- **Динамический layout.** Чтение cookie отключает статическую оптимизацию
  корневого layout. Для текущего приложения это ожидаемо; если появится
  требование к статике, понадобится клиентский выбор языка с неизбежной
  вспышкой языка.
- **`router.refresh()` и состояние.** Refresh перерисовывает RSC-дерево; в
  теории может сбросить локальное состояние серверных границ. Клиентские
  компоненты и `useState` сохраняются, но это нужно проверить вручную в
  комнате (вкладки, панель, iframe).
- **ICU-разметка.** Строки с `{name}` и HTML-подобной разметкой легко
  сломать; паритетный тест проверяет переменные, но не смысл перевода.
- **Дрейф каталогов.** `ru` может отставать от `en`; тест на одинаковый набор
  ключей обязателен в CI.
- **next-intl + webpack/Next 16.** Официально поддерживается, но сборку и
  тесты нужно прогнать до массовой миграции строк.
- **Тон перевода.** Русские тексты на главной неформальные; дословный
  английский будет звучать странно. Перевод делается по смыслу, файлы
  каталогов можно править без кода.
- **Объём diff.** ~319 строк в 19 файлах плюс 10 тестов; миграция идёт
  срезами, чтобы ревью оставалось обозримым.
- **Рефакторинг состояния.** Требование «переводить уже показанный текст»
  меняет типы reducer'а `GameTab` и состояния `use-room-packages`; это самая
  рискованная часть, её делаем отдельным срезом с тестами до миграции текста
  остальных экранов.
