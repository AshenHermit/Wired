# Вкладка «Для разработчиков» и dev log на Markdown

Дата: 2026-11-13
Статус: на согласовании

## Зачем

Документация по пакетам — единственное, что сейчас видит разработчик на главной,
но её список захардкожен в трёх местах (`DocsSidebar.tsx`, `DocsNav.tsx`,
`HomepageClient.tsx`), а содержимое тянется клиентским `fetch` из
`frontend/public/docs`. Добавить документ «просто положив файл» нельзя, и
рассказать, что изменилось на платформе, тоже негде: dev log отсутствует.

Нужна вкладка «Для разработчиков» — точка входа для тех, кто пишет пакеты:
документация плюс лента dev log, где каждая запись — markdown-файл в репозитории
с YAML front matter. Контент живёт рядом с кодом, проходит ревью в PR и не
требует ни БД, ни админки.

## Цели

- Вкладка на главной называется «Для разработчиков» (en — «For Developers»).
- Документация и dev log читаются из каталога контента; список файлов берётся из
  файловой системы, ручные массивы документов исчезают.
- Front matter валидируется схемой; битый файл валит `pnpm --filter frontend build`
  (а значит и сборку Docker-образа) с путём к файлу и причиной.
- Появляются постоянные адреса: `/docs` (хаб), `/docs/<slug>` (читалка),
  `/devlog` (лента), `/devlog/<slug>` (запись).
- На главной во вкладке: карточки документов из `content/docs`, три последние
  записи dev log, ссылка на полную ленту и на issues.
- Существующие четыре документа переезжают без изменения текста (меняется только
  положение H1 — см. «Контент»).
- В репозитории появляются пять тестовых записей dev log, основанных на недавней
  истории проекта.

## Не-цели

- CMS, админка, запись или редактирование из браузера.
- Изменения в `packages/server` и `packages/shared`, новые API-эндпоинты.
- Поиск, теги, комментарии, пагинация, черновики.
- Автогенерация ленты из git-коммитов.
- Мультиязычный контент: тексты записей и документации — русские, как и сейчас;
  переводятся только элементы интерфейса.

## Anti-goals

- Нельзя ломать существующие ссылки `/docs?doc=<slug>` — они редиректят на
  `/docs/<slug>`.
- Нельзя терять то, что уже работает в читалке: подсветку кода (highlight.js),
  GFM-таблицы, якоря заголовков и боковую навигацию. Якоря сейчас фактически
  сломаны для русского текста (см. «Ограничения») — это чинится здесь же.
- Нельзя добавлять CMS-подобный рантайм: контент остаётся в репозитории, запись
  публикуется через коммит и деплой.

## Ограничения

- Next.js 16 App Router, React 19. Фронтенд собирается в Docker
  (`frontend.Dockerfile`), финальный образ получает **production**-зависимости.
  Поэтому `yaml` — обычная зависимость; `tsx` (для скрипта валидации) — dev.
- **Весь App Router уже рендерится динамически.** Корневой `layout.tsx` делает
  `await getLocale()`, а `src/i18n/request.ts` читает cookie `NEXT_LOCALE` через
  `cookies()`. Поэтому `generateStaticParams` статического вывода не даст, и
  «контент читается на билде» в буквальном смысле здесь недостижимо. Принятая
  схема: контент читается на сервере при запросе из каталога, который есть в
  образе, а гарантию
  «битый файл виден до деплоя» даёт отдельный шаг валидации в `prebuild`.
- `WORKDIR /app/frontend`, то есть `process.cwd()` совпадает с корнем фронтенда и
  на билде, и в рантайме: `path.join(process.cwd(), 'content', ...)` работает в
  обоих случаях.
- `.dockerignore` исключает корневые `*.md` и корневую `docs/`; `frontend/content/`
  в контекст попадает и оказывается в образе. Контент нельзя складывать в
  корневой `docs/` — он вырезан из образа.
- `slugify` (`src/lib/markdown-parser.ts`) оставляет только `a-z0-9`, поэтому у
  русских заголовков получаются пустые id (`""`, `-1`, `-2`…), а ссылки ведут на
  `#`. Ссылки `](#...)` внутри документов не используются, но якоря и боковая
  навигация обязаны работать — значит парсер чинится в этой задаче:
  **кириллица транслитерируется в латиницу** (`## Что такое пакет` →
  `chto-takoe-paket`), латиница сохраняется как есть, остальные символы
  превращаются в дефисы. Таблица транслитерации живёт в `markdown-parser.ts`,
  внешняя зависимость не добавляется.
- Логика чтения использует `node:fs` и может импортироваться только серверным
  кодом; клиентские компоненты получают готовые данные пропсами.
- Строки интерфейса — в `frontend/messages/{en,ru}.json` (next-intl), в
  компонентах не хардкодятся.

## Подходы

**A. Контент-пайплайн в репозитории — выбран.**

Markdown + front matter рядом с кодом, сканирование `fs.readdir` на сервере,
`zod` для валидации, отдельный `prebuild`-шаг, который ловит битый контент до
сборки. Плюсы: git-история является ревью, нет БД и API, нет рантайм-зависимостей
от инфраструктуры, ошибка в front matter видна до деплоя. Минус: запись
публикуется через пересборку фронтенда и деплой — для dev log это приемлемо.

**B. Эндпоинт на NestJS, читающий каталог или таблицу — отклонён.**

Даёт публикацию без пересборки фронта и дорогу к админке, но требует модуля,
типов в `packages/shared`, решения вопросов доступа и кеширования. Ради ленты
текстов это лишняя точка отказа.

**C. Генерация из git-коммитов — отклонён как источник.**

`.git` исключён из Docker-контекста, а CI клонирует репозиторий с глубиной 1;
чтобы это заработало, пришлось бы тащить историю в образ и менять checkout.
Вдобавок коммиты не читаются как связный текст и не объясняют «зачем».

## Как это устроено

### Контент

- `frontend/content/docs/<slug>.md` — front matter: `title` (обязательно),
  `order` (опционально, число; по возрастанию, иначе по алфавиту).
- `frontend/content/devlog/YYYY-MM-DD-<slug>.md` — front matter: `title`, `date`,
  `summary`, `version` — все обязательны. `slug` — имя файла без даты и
  расширения; `date` — источник сортировки. Файлы, начинающиеся с `_`,
  игнорируются (`_template.md` служит образцом).
- Четыре документа переезжают из `frontend/public/docs/` в `frontend/content/docs/`
  под теми же именами. H1 каждого документа переезжает в `title`, из тела
  удаляется, потому что заголовок страницы рендерится из front matter. Остальной
  текст не меняется. `public/docs/` удаляется целиком.
- Пять тестовых записей: git-хранилище пакетов, загрузка только недостающих
  файлов, обслуживание/экспорт/починка git-хранилища, клиентский кеш пакетов,
  прогресс применения пакетов в Game tab. Тексты основаны на реальных коммитах,
  версии проставляются вручную (`0.4.0`, `0.4.1`, `0.5.0`), даты — 2026-11-08…13.
  Пользователь может править и удалять их как обычный контент.

### Модуль контента

`frontend/src/lib/content.ts` — единственное место, знающее о файловой системе:

- `listDocs()`, `getDoc(slug)`; `listDevlog()`, `getDevlogEntry(slug)`,
  `latestDevlog(limit)`.
- Схемы `zod` для обоих типов front matter; `yaml` — единственная новая
  рантайм-зависимость. `yaml` разбирает `date: 2026-11-13` как `Date`, поэтому
  дата нормализуется к строке `YYYY-MM-DD`.
- Ошибка парсинга или валидации бросается с путём файла и причиной.
- Чтения не кешируются: файлов единицы, чтение с диска дешевле кеша.
- Сортировка: документы по `order` (затем по `title`), записи по `date` по
  убыванию (при равенстве — по `title`).

### Валидация контента на билде

`frontend/scripts/validate-content.ts` — тонкая обёртка над тем же модулем:
перечисляет оба каталога, парсит каждый файл, печатает ошибки и выходит с
ненулевым кодом. Запускается через `tsx` в npm-скрипте `prebuild`, поэтому
срабатывает и при локальном `pnpm --filter frontend build`, и в Docker build
stage (`pnpm build:frontend`). В `verify` workflow добавляется отдельный дешёвый
шаг `pnpm --filter frontend validate:content`, чтобы битый файл всплывал до
SSH-деплоя, а не во время сборки образа.

### Маршруты

- `/docs` — хаб-список документов. При `?doc=<slug>` — `redirect()` на
  `/docs/<slug>`; это совместимость со ссылками из текущей главной.
- `/docs/<slug>` — читалка: боковая навигация (все документы + якоря текущего) и
  контент через существующий клиентский `MarkdownRenderer`; `generateMetadata` по
  front matter.
- `/devlog` — лента, плоский список по убыванию даты: дата, бейдж версии,
  заголовок, summary. Группировки по версиям нет.
- `/devlog/<slug>` — запись целиком и ссылки на соседние записи.

RSS-фида нет: решено не добавлять. Значит, не нужны ни route handler, ни
публичный origin из заголовков, ни правки конфига деплоя.

### Главная страница

`app/(browser)/(homepage)/page.tsx` становится async-серверным компонентом:
читает `listDocs()` и `latestDevlog(3)` и передаёт результат в `HomepageClient`
пропсами (сам клиент остаётся клиентским из-за zustand-стора). Содержимое вкладки
выносится в отдельный компонент `ForDevelopersTab` (документы + превью ленты +
issues), чтобы его можно было рендерить и тестировать без табов.
заголовок «Для разработчиков», карточки документов из front matter, блок
«Последние обновления» и ссылку «Все обновления» на `/devlog`; ссылка на issues
сохраняется. Захардкоженных ссылок на документы в `HomepageClient` не остаётся.

### Что удаляется и что переписывается

- Удаляются: `src/lib/doc-loader.ts` (и тест), `components/docs/DocsPage.tsx`
  (и тест), `components/docs/DocViewer.tsx` (и тест),
  `components/docs/DocsSidebar.tsx` (и тест), `components/docs/DocsNav.tsx`,
  `public/docs/`.
- `DocsSidebar` переписывается как серверный компонент, получающий список
  документов и якоря пропсами; клиентского состояния в нём не остаётся.
- `MarkdownRenderer` остаётся клиентским рендерером и получает строку.
- В `markdown-parser.ts` чинится `slugify` под Unicode (якоря вида
  `что-такое-пакет`), тесты парсера обновляются.

### i18n

- `Home.tabs.docs`: «Для разработчиков» / «For Developers».
- `Home.docs.*` переписывается под новую вкладку; `Home.docs.nav.*` удаляется,
  потому что названия документов приходят из front matter.
- Новые ключи для ленты и страниц записей (заголовки, «Все обновления», пустое
  состояние, подписи даты/версии).

### Проверка

- `pnpm --filter frontend validate:content` — падает на файле без `summary` или с
  битой датой.
- `pnpm --filter frontend check-types`, `pnpm --filter frontend lint`,
  `pnpm --filter frontend test`.
- Тесты: `content.test.ts` (разбор front matter, нормализация даты, сортировка,
  игнор `_`-файлов, ошибка на невалидном front matter), обновлённый
  `markdown-parser.test.ts` (транслитерация кириллицы, уникальность id, латиница
  без изменений), тест компонента вкладки `ForDevelopersTab` с пропсами
  (карточки документов и превью ленты).
- `pnpm --filter frontend build` — сборка проходит; `prebuild` валидирует контент.
- Ручная проверка: главная → вкладка, `/docs/<slug>` (якоря в сайдбаре работают),
  `/devlog`, запись, редирект `/docs?doc=getting-started`.

## Что остаётся на усмотрение исполнителя

- Точная вёрстка ленты и карточек (в рамках текущего стеклянного стиля),
  оформление бейджа версии.
- Нужен ли `order` всем четырём документам или достаточно алфавита.
- Содержимое `_template.md`.
- Внутренняя структура компонентов ленты (один компонент или список + карточка).
