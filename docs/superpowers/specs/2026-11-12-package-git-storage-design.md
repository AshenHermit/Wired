# Хранилище пакетов на git (внутренний движок)

Статус: черновик на ревью (после проверки ревьюером-исполнителем).

## Задача

Сейчас каждая публикация пакета — это полный снимок всех его файлов:

- клиент при каждом Emit собирает все файлы пакета из виртуальной ФС редактора
  (`publishPackageFiles` в `frontend/src/godot/bridge/package-sync.ts`),
  заливает их по одному и только потом публикует;
- сервер складывает снимок в `<packagesFilesDir>/<packageId>/revisions/<n>/`
  (`PackageStorageService.publishRevision`), а черновик — в `drafts/<n>/`;
- старые ревизии не удаляются никогда: GC ревизий нет вообще, есть только
  ретеншн runtime-артефактов (3 на `<package>/<room>/<revision>`) и удаление
  всего каталога пакета вместе с пакетом.

Отсюда два квадратичных роста. Диск: `N` публикаций × полный размер пакета.
Трафик: каждый Emit заново гоняет весь пакет, даже если изменился один `.gd`.

Нужно заменить хранение опубликованных байтов на **настоящий git** как
внутренний движок: пользователь по-прежнему жмёт Emit в WASM-редакторе, API и
номера ревизий не меняются, но сервер хранит каждый пакет как bare-репозиторий,
дедуплицирует блобы между ревизиями и принимает только недостающие файлы.

Git-remote, клонирование, push и LFS в эту фазу не входят.

## Что уже есть

- `ScriptingPackage` (`packages/server/src/database/entities/scripting-package.entity.ts`)
  хранит метаданные: `slug`, `name`, `version`, `description`, `previewImage`,
  `tags`, `enabled`, `room`, автора и участников. Метаданные к ревизии не
  относятся.
- `ScriptingPackageRevision` (`.../scripting-package-revision.entity.ts`):
  `revision` (int, unique в паре с пакетом), `status`
  (`draft`/`published`/`discarded`), `files` (jsonb-манифест
  `{filepath,size,sha256}[]`), `publishedAt`.
- `PackageRevisionsService` (`.../publish/package-revisions.service.ts`, 784
  строки): `createDraft`, `uploadFile`, `publish`, `publishCopiedRevision`,
  `getManifest`, `list`, `readPublishedFile`, `resolvePublishedFile`,
  `recordPinnedDependencies`.
- `PackageStorageService` (`.../storage/package-storage.service.ts`, 625 строк):
  layout `drafts/<n>`, `revisions/<n>`, `pins/<n>.json`; проверка манифеста
  (`assertMatchesManifest`), атомарная публикация через `rename`, rewrite
  ревизий для переименования slug (`beginRewrite`), `removePackage`.
- Ограничения манифеста (`.../storage/package-manifest.ts`): 2000 файлов,
  64 MiB на файл, 256 MiB на ревизию; пути нормализуются и проверяются на
  traversal и регистронезависимые дубликаты (`.../storage/package-path.ts`,
  `src/common/paths.ts`).
- Загрузка файла идёт через multer в память
  (`POST :id/revisions/:revision/files/*path`,
  `FileInterceptor` с лимитом 64 MiB).
- Публикация сериализуется `PackagePublishLockService` — advisory-lock в
  Postgres плюс in-process set; тот же лок держит переименование slug.
- `PackageClosureResolver` (`.../publish/package-closure-resolver.ts`) читает
  ровно указанную ревизию, идёт по пинам зависимостей
  (`pins/<n>.json`), проверяет published/room/циклы и считает `artifactKey`
  как sha256 от списка `(packageId, revision)` замыкания + версия asset-bake.
- `PackageDeliveryService` (`.../delivery/package-delivery.service.ts`) собирает
  из этих байтов runtime-артефакт в
  `<packageRoot>/runtime/v2/<room>/<revision>/<artifactKey>/`: переписывает
  `res://packages/...` на runtime-пути, запекает glTF, пишет `manifest.json`.
  Файлы артефакта читаются с диска (`resolveRuntimeFile` → `createReadStream`).
- Переименование slug (`ScriptingPackagesService.renameSlug`,
  `.../scripting-packages.service.ts:657`) внутри транзакции переписывает
  байты опубликованных ревизий и черновиков, затем двигает slug, инвалидирует
  артефакты (`invalidatePackage`) и рассылает `packagesChanged`.
- Клиент уже получает sha256 каждого файла из плагина редактора:
  `collectFiles` (`frontend/src/godot/bridge/godot-packages-fs.ts:252`)
  возвращает `{entry:{filepath,size,sha256}, contents}`, и
  `createPackageRevision` отправляет этот манифест как есть.
- Деплой: backend-образ `backend.Dockerfile` (Node 22 bookworm-slim) сейчас
  **не содержит git**; данные лежат на volume `wired_storage`
  (`/app/storage`), схема БД — `DB_SYNC=1` без миграций.

## Цели

- Один bare-репозиторий на пакет; опубликованная ревизия — коммит с тегом
  `refs/tags/revisions/<n>`.
- Дедупликация содержимого: одинаковые файлы между ревизиями хранятся один раз.
- Инкрементальная публикация: клиент заливает только то, чего у сервера нет.
- Сохранить без изменений внешний контракт: номера ревизий, манифесты, чтение
  файлов, копирование, доставку, пины, переименование slug.
- Старые опубликованные ревизии остаются доступными навсегда: на них ссылаются
  пины и артефакты других пакетов.
- Существующие пакеты переводятся без простоя и без большого миграционного
  прогона.

## Не-цели

- Git-remote: `clone`/`push`, smart HTTP, авторизация по basic, LFS.
- Ветки, merge, конфликты, PR-подобные сценарии.
- Пользовательский UI истории: список ревизий, diff, откат. `GET /revisions`
  остаётся как есть и по-прежнему не используется интерфейсом.
- Версионирование метаданных пакета в git (имя, описание, теги, превью
  остаются в Postgres).
- Общий объектный store между пакетами: дедуп только внутри одного пакета.
- Изменение формата runtime-артефактов, кроме ключа и версии каталога.

## Анти-цели

- Сервер не делает checkout и не применяет фильтры из репозитория.
- Git не участвует в авторизации и видимости: права проверяются до чтения.
- Нельзя ломать `DB_SYNC`: изменение схемы только аддитивное и nullable.
- Нельзя терять старые ревизии: удаление тега опубликованной ревизии — ошибка.
- Нельзя отдавать клиенту commit SHA как замену номера ревизии: номер остаётся
  публичным идентификатором в путях и манифестах.
- Нельзя доверять oid блоба как проверке содержимого: git хеширует
  `"blob <len>\\0" + bytes`, поэтому oid ≠ sha256 файла.

## Подходы

Рассматривались три варианта хранения.

1. **Оставить снимки каталогов.** Дёшево сейчас, но роста нет предела, а
   трафик публикации не уменьшается. Отклонено.
2. **Content-addressed store без git** (`objects/<sha256>` + манифест ревизии).
   Даёт дедуп и инкрементальную загрузку, но нет стандартного инструментария:
   ни `git log`, ни `fsck`, ни привычного формата для будущего экспорта.
   Отклонено: пользователь выбрал настоящий git.
3. **Bare-репозиторий на пакет, доступ только через plumbing-команды.**
   Выбрано.

Внутри варианта 3 доступ к git можно сделать тремя способами:

- **a. Спавнить `git` на каждую операцию.** Просто, но на артефакт из 2000
  файлов это 2000 процессов и десятки секунд.
- **b. Пакетные plumbing-вызовы:** один процесс на пачку блобов
  (`hash-object --stdin-paths`), временный index + `write-tree` для дерева,
  один `commit-tree`, один `update-ref`; чтение — `cat-file --batch` на весь
  набор oid. Выбрано.
- **c. `isomorphic-git` в Node.** Не нужен бинарник в образе, но медленнее на
  больших пакетах и хуже предсказуем. Оставлено как запасной путь, если
  добавление `git` в образ окажется проблемой.

## Устройство

### Layout

```
<packagesFilesDir>/<packageId>/
  repo.git/                 # bare-репозиторий, object-format=sha256
  drafts/<n>/...            # staging черновика, как сейчас
  pins/<n>.json             # как сейчас: {dependencies:[{packageId,revision}]}
  revisions/<n>/...         # legacy, только чтение до конвертации
  runtime/v3/...            # runtime-артефакты (версия поднимается)
```

`repo.git` создаётся при первой git-публикации или конвертации.
Наличие `repo.git` — признак, что пакет переведён; отдельного поля в БД не
нужно.

### Формат объектов и индекс содержимого

`git init --bare --object-format=sha256`. Debian bookworm несёт git 2.39,
поддержка SHA-256 есть с 2.29; Git for Windows тоже умеет. Remote-
совместимость не нужна: репозитории не покидают сервер.

Важно: **oid блоба не совпадает с sha256 файла.** Git считает
`sha256("blob <len>\\0" + bytes)`. Поэтому дедуп и ответ «этого файла у меня
нет» нельзя получить напрямую из object store; нужен индекс содержимого.

SHA-256 выбран не ради совпадения oid и sha256, а ради устойчивости к
коллизиям: дедуп адресуется содержимым, и подмена одного файла другим через
коллизию хеша недопустима. Цена — 64-символьные oid и необходимость индекса;
на фоне остального это дёшево.

Индекс содержимого — производная структура, **не источник истины**:

- `Map<sha256, oid>` на пакет, строится лениво из уже опубликованных ревизий:
  для каждой строки `files[]` (path → sha256) берётся `ls-tree -r` её коммита
  (path → oid) и заполняется соответствие;
- хранится в памяти процесса и инвалидируется при публикации, rewrite и
  миграции (после успешной операции в него дописываются новые пары);
- при холодном старте цена — по одному `ls-tree` на опубликованную ревизию
  пакета, только при первом `createDraft`/публикации после рестарта;
- если пара в индексе есть, сервер всё равно проверяет `cat-file
  --batch-check` одним процессом, что oid существует; отсутствующие пары
  считаются missing и вычищаются из индекса;
- индекс можно потерять без последствий: он пересобирается из БД и деревьев.

Settings репозитория при создании:

- `core.autocrlf=false`, `core.symlinks=false`, `core.fsmonitor=false`;
- `core.hooksPath` — пустой каталог (plumbing-хуки всё равно не запускаются,
  но так спокойнее);
- `gc.auto=0`: сборка мусора только плановым заданием.

Все команды запускаются с `GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`,
изолированным `HOME` и массивом аргументов (без shell).

### Конвенции репозитория

- `refs/tags/revisions/<n>` — коммит опубликованной ревизии. Лёгкий тег, без
  tag-объекта.
- `refs/heads/main` — тот же коммит последней опубликованной ревизии (удобно
  для `git log`, `git show`, будущего экспорта).
- `refs/pending/<kind>/<n>` — временная ссылка на подготовленный, но ещё не
  подтверждённый БД коммит (публикация или rewrite). Живёт только между
  созданием коммита и фиксацией в БД; подробности в разделах ниже.
- История линейная: parent нового коммита — коммит предыдущей опубликованной
  ревизии пакета.
- В дереве только файлы пакета. Служебных файлов (`.wired/...`,
  `.gitattributes`) нет: атрибуты и фильтры не нужны и опасны.
- Режим всех записей `100644`; symlink (`120000`) и submodule (`160000`)
  отвергаются на входе и проверяются при чтении дерева.
- Автор коммита — автор пакета (`name <email>`), коммиттер — он же; сообщение
  `revision <n>`. Дата — `publishedAt`.

### Модель данных

Единственное изменение схемы: nullable-колонка

```ts
@Column({ type: 'varchar', length: 64, nullable: true })
commitSha: string | null;
```

в `ScriptingPackageRevision`. `DB_SYNC` добавит её сам; откат кода оставит
колонку, что безвредно. Существующие строки получают `NULL` и читаются из
`revisions/<n>/` (dual-read), пока пакет не сконвертирован.

`files` (jsonb) остаётся манифестом и источником истины для API. Git-дерево
обязано ему соответствовать; расхождение — ошибка чтения, а не тихая подмена.
Манифест проверяется при публикации, а не пересчитывается на каждом чтении.

### Сборка дерева

`mktree` умеет только один уровень и падает на путях со `/`, поэтому дерево
собирается через временный index:

```
GIT_INDEX_FILE=<tmp> git update-index -z --index-info   # строки:
  100644 blob <oid>\t<path>\0
GIT_INDEX_FILE=<tmp> git write-tree                      # → root tree oid
```

Два процесса на ревизию, любой уровень вложенности. Временный файл живёт в
`<packageRoot>/tmp/` и удаляется в `finally`; при падении его подбирает
периодическая уборка. Альтернатива — `fast-import` одним потоком, но она
менее прозрачна при ошибках и оставлена на потом.

### Публикация

Порядок под уже существующим publish-lock:

1. `createDraft` сначала мирит незавершённые операции пакета (см.
   «Восстановление»), затем проверяет манифест (как сейчас) и возвращает
   `missing` — список объявленных путей, чьего sha256 нет в индексе
   содержимого. Если репозитория ещё нет, все файлы missing.
2. Клиент заливает только `missing`; остальные файлы пропускает, не читая
   байты повторно (`collectFiles` уже держит их в памяти, но пропуск важен для
   трафика).
3. `uploadFile` пишет staging-файл, как сейчас, и сверяет размер/sha256.
   Дубликаты содержимого в разных путях заливаются по путям, но в git
   попадают одним блобом.
4. `publish`:
   - проверить staged-файлы (набор ⊆ манифеста, размер и sha256 совпадают);
   - для каждого объявленного пути взять oid: из staged-файла через
     `hash-object -w --stdin-paths` (пачками) либо из индекса содержимого;
   - для всех oid, взятых из индекса, одним `cat-file --batch-check`
     убедиться, что объекты существуют; иначе 409 `package_storage_stale` и
     клиент повторяет загрузку;
   - собрать tree через временный index + `write-tree`;
   - `commit-tree` с parent = коммит предыдущей опубликованной ревизии;
   - создать `refs/pending/publish/<n>` на новый коммит;
   - транзакция БД: `status='published'`, `publishedAt`, `commitSha`;
   - закоммитить транзакцию;
   - одной `update-ref --stdin` транзакцией поставить
     `refs/tags/revisions/<n>`, обновить `refs/heads/main` и удалить pending
     ref (с ожидаемыми старыми значениями, чтобы поймать гонку);
   - дописать пары в индекс содержимого, удалить `drafts/<n>`, записать пины,
     разослать `dispatchPublished`.
5. Если `update-ref` упал, БД уже published, pending ref цел: следующий
   вход в пакет (чтение, публикация, GC) доделывает перестановку тегов и
   удаляет pending. Клиент получает ошибку и может повторить; повторный
   `publish` идемпотентен.
6. Если упала транзакция БД, pending ref существует, строка осталась draft:
   миринг удаляет pending, staging остаётся, клиент повторяет. Опубликованные
   теги при этом никогда не становятся сиротами.

Повторный `publish` опубликованной ревизии идемпотентен, как сейчас.

### Инкрементальная загрузка

`POST /:id/revisions` уже принимает `files[]` с sha256, поэтому новый ответ
просто добавляет поле:

```ts
type PackageRevisionDraft = PackageRevision & { missing: string[] };
```

`missing` — пути, а не хеши: два одинаковых файла в разных путях должны быть
залиты оба (сервер потом всё равно хранит один блоб). Старые клиенты поле
игнорируют и ведут себя как раньше — контракт обратно совместим.

Отдельного заголовка `X-Wired-Content-Sha256` нет: сервер не может вернуть
осмысленный ответ «уже есть» без чтения блоба, а клиент и так пропускает
такие файлы по `missing`.

Если `missing` не пришёл (старый сервер/клиент), клиент заливает всё, как
сейчас.

### Чтение

Новый `PackageGitStorage` (или методы в `PackageStorageService`) закрывает
доступ к байтам:

- `resolveCommit(packageId, revision)` — для published-строки сначала
  `commitSha` (если объект существует), иначе тег; для legacy — `null`.
  Несовпадение `commitSha` и тега — попытка доделать pending-перестановку,
  иначе предупреждение и запись тега как истины (см. «Восстановление»).
- `listTree(commit)` — `ls-tree -r -z`, кэш `commit → Map<path, oid>` (LRU на
  50 коммитов). Дерево маленькое (≤2000 записей), кэш дешёвый.
- `forEachBlob(oids, cb)` — один `cat-file --batch` на весь набор: читает
  заголовок и содержимое по одному, отдаёт в колбэк и сразу освобождает
  буфер. Так собирается артефакт и копируются пакеты: один процесс, память
  ограничена одним файлом (≤64 MiB), а не всей ревизией.
- `readFiles(commit, paths)` — обёртка над `forEachBlob` для случаев, когда
  байты нужны целиком (копирование, пины, rewrite).
- `openFile(commit, path)` — `cat-file blob <oid>` с stdout-стримом для
  HTTP-отдачи, чтобы не буферизовать 64 MiB на каждый запрос.

`PackageRevisionsService.resolvePublishedFile` меняет форму результата с
`{path,size}` на `{stream,size}`; контроллер отдаёт `StreamableFile(stream)`.
`readPublishedFile` остаётся буферным для замыкания и копирования.

Важно: существующие вызовы `readPublishedFile` по одному файлу
(`PackageClosureResolver.readFileBytes`, `publishCopiedRevision`,
`recordPinnedDependencies`) переводятся на batch-чтение ревизии: иначе на
каждую ревизию из 2000 файлов будет 2000 процессов, и сборка артефакта станет
медленнее, чем сейчас.

### Пины и замыкание

Формат пинов не меняется: `{dependencies:[{packageId, revision}]}`. Это
осознанно: переименование slug двигает тег ревизии, номер ревизии остаётся
стабильным ключом, а commit sha резолвится из тега в момент чтения. Если
хранить в пинах sha, пришлось бы обходить и переписывать пины всех зависимых
пакетов при каждом переименовании.

`PackageClosureResolver` продолжает грузить строку по номеру ревизии, но байты
читает через git (или legacy) пакетно. `artifactKey` теперь считается по
`(packageId, commitSha)` для git-пакетов и `(packageId, 'legacy:<revision>')`
для непереведённых; версия формата артефактов поднимается до `v3`, старые
каталоги `runtime/v2` удаляются при первом обращении/инвалидации, чтобы не
копились.

### Черновики и GC

Черновик остаётся staging-каталогом. Блобы пишутся в репозиторий только на
публикации, поэтому вытесненные и брошенные черновики не оставляют мусора в
git. Недостижимые объекты появляются после неудачных публикаций и rewrite —
их подбирает GC.

GC: плановое задание (раз в сутки, плюс вручную командой) по каждому
репозиторию:

- сначала миринг pending-ссылок (иначе они держат объекты живыми);
- `git repack -adq` и `git prune --expire=2.weeks.ago`;
- только под publish-lock пакета, чтобы не пересечься с публикацией;
- ошибки логируются и не роняют процесс; `gc.auto=0` гарантирует, что git не
  запустит сборку сам в неподходящий момент.

Опубликованные теги не удаляются никогда. Ретеншн ревизий, как и сейчас,
отсутствует.

### Восстановление после сбоев

Единое правило: pending ref — это намерение, тег — факт, БД — манифест.

При любом входе в пакет (createDraft, publish, чтение, GC) выполняется
`reconcilePackage`:

1. Для каждого `refs/pending/<kind>/<n>`:
   - если строка ревизии published и `commitSha` совпадает с oid pending —
     доделать шаг `update-ref` (тег и `main`), удалить pending;
   - если строка draft/discarded или `commitSha` другой — удалить pending
     (объекты станут недостижимыми, их соберёт GC). Данные не теряются:
     staging черновика цел, клиент повторит публикацию.
2. Для draft-строки, у которой уже есть опубликованный тег (ручное
   вмешательство или старая версия кода), — «повысить» строку до published:
   `commitSha` из тега, `publishedAt` из коммита. Поэтому `discardDrafts` и
   `createDraft` никогда не выбрасывают опубликованную ревизию: сначала
   миринг, потом discard.
3. Parent для следующего коммита выбирается по published-строкам, а не по
   тегам, поэтому осиротевший pending не влияет на историю.

### Переименование slug

`beginRewrite` перестаёт копировать каталоги. Для каждой затронутой
опубликованной ревизии:

1. прочитать дерево и все файлы (batch);
2. применить `rewriteSlugReferences` к текстовым файлам;
3. записать новые блобы, собрать tree/commit (parent — предыдущая ревизия);
4. создать `refs/pending/rewrite/<n>`;
5. в транзакции БД обновить `files[]` (sha256 изменившихся файлов) и
   `commitSha` (не коммитить);
6. закоммитить БД;
7. одной `update-ref --stdin` транзакцией переставить теги, обновить `main` и
   удалить pending.

Сбой на шаге 3–5 откатывает БД, pending удаляется мирингом, старые теги целы.
Сбой между 6 и 7 оставляет published-строки с новым `commitSha` и pending:
миринг доделывает теги. В любом состоянии чтение идёт по `commitSha`, поэтому
байты и манифест остаются согласованными.

Старые коммиты становятся недостижимыми и уходят в GC. Черновики
переписываются как раньше — они лежат в staging.

`invalidatePackage` и `packagesChanged` остаются: кэш замыкания и in-memory
артефакты надо сбросить, несмотря на новый `artifactKey`.

### Копирование (workshop, fork, room-copy)

`publishCopiedRevision` не меняется по смыслу: он читает исходную ревизию
целиком (batch), применяет `transformFile`, пишет staging нового пакета и
вызывает обычную публикацию. Дополнительных путей в git не появляется; дедуп
работает внутри целевого пакета.

### Миграция

Конвертация пакета идемпотентна и выполняется под publish-lock. Перед ней —
`reconcilePackage`.

1. Для каждой published-строки без `commitSha` по возрастанию ревизии:
   прочитать `revisions/<n>/`, сверить размер и sha256 каждого файла с
   манифестом, записать блобы (`hash-object -w --stdin-paths`), собрать
   tree/commit с parent от предыдущего коммита, поставить тег, записать
   `commitSha` в БД.
2. Legacy-каталог не удаляется сразу: он остаётся страховкой и удаляется
   отдельной командой очистки после успешной проверки (`git fsck
   --connectivity-only` и совпадение тегов со всеми строками).

Триггеры:

- лениво при первой записи в пакет (publish, copy, rename) — основной путь;
- CLI `pnpm --filter server packages:git-migrate -- --all|--package <id>`
  (скрипт в `packages/server/scripts`) — для пакетной миграции и продакшена;
- опционально `WIRED_PACKAGE_GIT_AUTOMIGRATE=1` на старте для dev-базы.

Чтение до конвертации идёт из `revisions/<n>/`; после появления `repo.git` —
из git. Смешанное состояние корректно.

### Отказоустойчивость

- **Git недоступен/старая версия.** При `WIRED_PACKAGE_GIT_STORAGE=1` сервер на
  старте проверяет `git --version` (нужен ≥2.29) и падает с внятной ошибкой.
- **Процесс git упал/таймаут.** Обёртка убивает процесс, возвращает
  `package_storage_failed` 503; публикация не меняет теги.
- **Диск заполнен.** `hash-object`/`write-tree` падают до создания pending;
  видимое состояние не меняется, мусор подбирает GC.
- **Гонка публикаций.** Publish-lock + `update-ref` с ожидаемым старым oid.
- **Тег есть, строка draft.** Promote при миринге (см. выше).
- **Строка published, тега нет.** Если pending есть — доделать; иначе если
  есть legacy-каталог — читаем его и логируем; иначе
  `package_revision_missing` 500 и команда `packages:git-repair`.
- **Индекс содержимого устарел/потерян.** Пересобирается из манифестов и
  деревьев; отсутствующие oid проверяются `cat-file --batch-check`.
- **Повреждённый репозиторий.** `git fsck --connectivity-only` в GC-задании;
  при ошибке пакет читается из legacy-каталога, если он ещё есть, иначе
  ошибка на чтение (не тихая подмена).

### Безопасность

- Никакого checkout/archive/`git apply`; только plumbing.
- Пути уже валидируются (`normalizeRelativePath`); дополнительно проверяется,
  что в дереве нет symlink/submodule и нет сегмента `.git`.
- `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` указывает на пустой файл,
  `GIT_TERMINAL_PROMPT=0`; аргументы передаются массивом.
- Права на репозитории — только процессу сервера (0700).
- `git` не решает, кто может читать пакет: `assertVisible`/гарды остаются
  перед любым чтением.

### Эксплуатация и деплой

- В `backend.Dockerfile` в финальную стадию добавляется пакет `git`
  (bookworm → 2.39). Образ вырастает примерно на 50 МБ.
- Репозитории лежат на том же volume `wired_storage`, что и сейчас; бэкап
  volume покрывает их. Восстановление — volume + БД; теги — источник истины
  для байтов.
- Плановый GC/`fsck` — отдельный скрипт и/или таймер в процессе; вручную —
  `pnpm --filter server packages:git-maintenance`.
- Метрики/логи: размер репозитория, число объектов, длительность git-команд,
  `{packageId, revision, commit, blobsWritten, bytesUploaded}` на публикацию.

## Внедрение и откат

Флаг `WIRED_PACKAGE_GIT_STORAGE` (по умолчанию `0` до проверки) решает, куда
пишутся **новые** пакеты:

- `0` — новые пакеты публикуются старым путём в `revisions/<n>/`;
- `1` — новые публикации идут в git.

Путь записи для уже существующего пакета определяется его состоянием, а не
флагом: если `repo.git` есть — пишем в git (иначе сконвертированный пакет
нельзя было бы публиковать при выключенном флаге), иначе по флагу. `missing`
возвращается только когда путь записи — git; на legacy-пути клиент заливает
всё, как раньше. Чтение всегда выбирает git, если `repo.git` есть.

Порядок выката:

1. Добавить git в образ, код читает оба формата, флаг выключен.
2. Включить на dev, прогнать тесты и ручные сценарии (публикация, зависимость,
   копирование, переименование slug).
3. Прогнать миграцию на копии прод-данных, замерить время и размер.
4. Включить флаг на проде; старые пакеты конвертируются при первой записи или
   командой.
5. Через неделю — команда очистки legacy-каталогов.

Откат до конвертации — выключить флаг. После конвертации чистого отката нет:
новые ревизии существуют только в git, поэтому для возврата нужна обратная
команда `packages:git-export`, которая разложит ревизии в `revisions/<n>/`.
Это осознанная цена; команда входит в объём работ.

## Тесты

- Новый `package-git-storage.service.spec.ts`: реальный `git` во временных
  каталогах — init, публикация двух ревизий, вложенные каталоги, дедуп (один
  блоб на два одинаковых файла), чтение, теги, `fsck`.
- Обновить спеки: `package-storage.service.spec.ts`,
  `package-revisions.service.spec.ts`, `package-closure-resolver.spec.ts`,
  `package-delivery.service.spec.ts`, `package-workshop.service.spec.ts`,
  `scripting-packages.service.spec.ts` (rewrite), `scripting-packages.controller.spec.ts`,
  `package-sync.service.spec.ts`.
- Сценарии: вторая публикация с одним изменённым файлом заливает только его;
  публикация без изменений не заливает ничего; повторная публикация с
  удалённым-и-возвращённым файлом; rewrite двигает тег, обновляет `files[]` и
  инвалидирует артефакт; миграция legacy-пакета; восстановление после падения
  между pending ref и БД; гонка двух публикаций; битый oid в индексе.
- Фронтенд: `package-sync.test.ts` — пропуск `missing`, прогресс, обратная
  совместимость (нет `missing` → заливаем всё).
- Интеграция с реальным git в CI: ubuntu-latest и Git for Windows содержат
  git; тест падает, если бинарника нет (лучше явная ошибка, чем тихий skip).

## Принятые решения (мои, можно оспорить)

1. Один bare-репозиторий на пакет, только серверный доступ, без remote и LFS.
2. `object-format=sha256` — ради устойчивости к коллизиям при дедупе по
   содержимому; oid ≠ sha256, поэтому есть производный индекс
   `sha256 → oid`, пересобираемый из манифестов и деревьев.
3. Тег на каждую ревизию, `main` как зеркало последней, линейная история,
   pending-ссылки для незавершённых операций.
4. Черновики остаются staging-каталогами; блобы пишутся в git только при
   публикации; брошенные черновики не мусорят репозиторий.
5. `missing` в ответе `createDraft` (пути, по sha256 из индекса); клиент
   заливает только недостающие файлы; старые клиенты работают без изменений.
6. Пины остаются `{packageId, revision}`; commit sha резолвится из
   `commitSha`/тега, чтобы переименование slug не требовало обхода зависимых
   пакетов.
7. `artifactKey` — sha256 от `(packageId, commitSha)` замыкания (legacy —
   `legacy:<n>`); версия каталога артефактов поднимается до `v3`.
8. Чтение выбирает git/legacy по наличию `repo.git`; путь записи — тоже
   (флаг только для новых пакетов); миграция ленивая плюс CLI.
9. GC — плановый `repack` + `prune --expire=2.weeks.ago`, только под
   publish-lock; опубликованные теги не удаляются.
10. Дерево собирается временным index + `write-tree`; дерево не строится
    `mktree` (он одноуровневый).
11. Метаданные пакета в git не переносятся; истории в UI нет.

## Открытые вопросы

Нет вопросов, блокирующих план. Известная цена решения: холодная сборка
индекса содержимого — один `ls-tree` на опубликованную ревизию при первом
обращении после рестарта; при необходимости позже добавляется персистентный
кэш, но это не влияет на план.
