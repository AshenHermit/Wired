# Бесшовная двухфазная замена мира при hot reload

## Намерение

При публикации новой версии пакета игроки не должны проваливаться сквозь временно исчезнувшие статические объекты. Новая версия мира должна быть подготовлена до удаления старой, а переключение должно происходить за один короткий commit-переход.

## Текущее поведение

`MainScene._apply_registered_package()` сначала паркует/удаляет динамические сущности, затем `StaticWorldContainer.rebuild()` вызывает `clear()` и освобождает старые статические сцены, после чего создаются новые сцены и восстанавливаются сущности. В промежутке физические коллайдеры отсутствуют.

## Цели

- Не оставлять игроков без пола/коробок во время применения новой ревизии.
- Подготавливать новую статическую геометрию до удаления старой.
- Сохранять состояние и entity ID динамических объектов на сервере.
- Не ломать сетевую репликацию, late join и snapshot/reconcile.
- Сохранить текущую модель публикации и порядок применения пакетов.

## Не входит в задачу

- Полное patch-in-place обновление отдельных узлов.
- Перенос существующих Godot-узлов между ревизиями.
- Изменение формата package manifest или backend API.
- Гарантия отсутствия визуального перехода, если новая геометрия намеренно удаляет поверхность под игроком.

## Предлагаемый поток

1. `PackagesManager` скачивает, проверяет и материализует новую ревизию как сейчас.
2. Registry регистрирует новую версию пакета, но старая сцена ещё остаётся в дереве.
3. `StaticWorldContainer` инстанцирует новые зарегистрированные корни во временный набор/контейнер и проверяет, что они созданы.
4. Сервер сохраняет состояние динамических сущностей пакета и подготавливает их новые экземпляры с теми же `entity_id` и состоянием; до commit старые экземпляры продолжают существовать.
5. Перед commit сохраняется состояние игроков: transform и физические параметры, необходимые для восстановления после короткого перехода.
6. В одном commit-шаге новые статические и динамические объекты становятся активными, старые объекты отсоединяются и освобождаются только после того, как новые уже добавлены в дерево и прошли physics-сynchronization.
7. Состояние игроков возвращается на сохранённые transform/velocity, после чего физика снова включается.
8. Сервер уведомляет клиентов через существующий hot-reload barrier/snapshot-механизм. Клиенты применяют ту же двухфазную замену своих локальных копий; authoritative entity ID и snapshot остаются источником истины.

## Контракт переключения

- До commit старая геометрия продолжает участвовать в физике.
- После подготовки новая геометрия уже находится в сцене.
- Удаление старых узлов не выполняется через `clear()` до завершения подготовки.
- При ошибке подготовки новая версия отбрасывается, старая остаётся активной.
- При commit нельзя одновременно запускать другой package operation; существующая очередь операций сохраняется.

## Изменения по компонентам

- `static_world_container.gd`: разделить подготовку нового набора сцен и commit; старый набор хранить до успешного переключения.
- `dynamic_world_container.gd`: добавить staged replacement/restore для сущностей пакета без потери entity ID, записи состояния или сетевого контракта.
- `main_scene.gd`: заменить последовательность park → rebuild → restore на prepare → commit → cleanup и связать её с текущим barrier.
- `players_manager.gd`/`wired_player.gd`: добавить снимок и восстановление физического состояния игроков вокруг commit, если одного physics-frame недостаточно.
- Тесты Godot smoke: проверить отсутствие пустого кадра физики, сохранение entity ID/позиции и восстановление игроков при package reload; проверить rollback при ошибке инстанцирования.

## Рассмотренные подходы

1. **Двухфазная замена мира — выбранный подход.** Сохраняет старый мир до готовности нового и минимизирует окно риска; требует staged API и аккуратного commit.
2. **Заморозка игроков.** Проще, но маскирует отсутствие геометрии и не решает скачки/десинхронизацию динамических объектов.
3. **Patch-in-place.** Потенциально самый бесшовный, но требует отдельной системы diff для сцен, коллайдеров и скриптов; не подходит как первый шаг.

## Критерии готовности

- Во время успешного reload игроки не проваливаются из-за временного отсутствия старой геометрии.
- Старые и новые статические объекты не дублируются после commit.
- Динамические entity ID, состояние и server/client snapshots остаются согласованными.
- Ошибка подготовки не уничтожает предыдущую рабочую версию.
- Существующие server/frontend тесты проходят, добавлены тесты для staged reload.
