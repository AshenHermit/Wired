# Клиентский кеш ревизий пакетов в Game tab

Дата: 2026-11-13
Статус: на согласовании

## Зачем

Сейчас Game tab при каждом старте заново скачивает все файлы пакетов комнаты,
даже если ровно эти же байты уже лежат в браузере. При полной перезагрузке
страницы файлы физически переживают её (web-экспорт хранит `user://` в IDBFS
поверх IndexedDB), но клиент их не использует: пропуск загрузки решается только
по номеру ревизии, а свежий вызов обязан "обновить" артефакт, даже когда
`artifactKey` совпадает.

Вторая проблема — место хранения. `user://` игры и `user://` WASM-редактора,
который живёт в той же странице комнаты, — одна и та же база IndexedDB. IDBFS
синхронизирует in-memory дерево целиком, включая удаления, поэтому сброс одного
инстанса стирает в базе то, что записал другой. Кеш пакетов должен лежать в
отдельной базе, которую редактор не монтирует.

Цель: при старте игры переиспользовать уже материализованный артефакт с тем же
`artifactKey` без скачивания файлов, сохраняя корректность при переопубликации
зависимостей.

## Цели

- После полной перезагрузки страницы пакет с тем же `artifactKey` применяется
  локально: файлы не скачиваются, `sync_package` завершается успешно и
  публикует состояние как при обычном применении.
- Битые или неполные локальные данные никогда не используются: проверка перед
  переиспользованием, при провале — обычное скачивание.
- Изменённый `artifactKey` (переопубликована зависимость) ведёт себя как
  сегодня: новый каталог, полная загрузка.
- Кеш пакетов не стирается WASM-редактором комнаты: он лежит в отдельной
  IndexedDB-базе, а не в общем `/userfs`.
- Никаких изменений API, сервера и фронтенда.

## Не-цели

- Кеширование HTTP-ответов (`Cache-Control`, Service Worker, Cache API).
  Сервер отдаёт `no-store` намеренно, а одноразовый `token` в URL всё равно
  ломает ключ кеша.
- Дельта-загрузка (только изменившиеся файлы). При смене ключа грузим пакет
  целиком, как сейчас.
- Новая политика вытеснения/лимит объёма: `prune` уже держит применённый
  артефакт плюс самую новую другую ревизию на пакет. Кеш не увеличивает
  установившийся объём по сравнению с текущим поведением.
- Кеш между разными браузерами/устройствами и на сервере.
- Перенос остальных данных `user://` (настройки, логи, состояние клиента) в
  отдельное хранилище: изолируется только кеш пакетов.

## Анти-цели

- Нельзя считать локальный каталог валидным только по имени: без маркера
  завершённой записи частично записанный каталог может выглядеть полным.
- Нельзя ослаблять проверку целостности: использование файлов с чужим
  `artifactKey` смешает два состояния библиотеки.
- Нельзя оставлять без инвалидации клиентские производные файлы
  (`AssetDeriver`): смена правил преобразования не меняет `artifactKey` и иначе
  молча не доедет до пользователя с готовым кешем.

## Ограничения

- GDScript 4.8; клиент и нативный runtime используют один и тот же
  `packages_manager.gd`.
- `user://` в web — IDBFS, физически `/userfs/app_userdata/<project>`;
  конкретный путь зашит в движке, перенаправить `user://` нельзя. Запись
  durable только после `FS.syncfs`; в проекте это делает
  `JavaScriptBridge.force_fs_sync()` (сейчас вызывается только редактором в
  `addons/wired_bridge/plugin.gd`).
- Список постоянных каталогов web-экспорта приходит из конфига загрузчика
  (`persistentPaths`, по умолчанию `['/userfs']`). Каждый путь монтируется как
  отдельная база IDBFS, имя базы — путь монтирования. Массив переопределяется в
  нашем shell (`_wired/web/shell.html`) через
  `engine.startGame({persistentPaths: [...]})`: `EngineConfig.update` копирует
  известные ключи, а `Engine.init` монтирует все перечисленные пути (проверено
  по `packages/server/game_export/web/index.js`).
- `/userfs` остаётся в списке: `user://` движка, его настройки и логи продолжают
  жить там.
- База `/wired-cache` принадлежит только игре: редактор её не монтирует и не
  может из неё ничего удалить.
- `artifactKey` — content-addressed идентификатор замыкания (sha256 по
  `(packageId, commitSha)`); одинаковый ключ означает одинаковые байты.
  Это единственная гарантия, на которую опирается переиспользование.
- `artifactKey` приходит в runtime-manifest до скачивания файлов, а `slug` —
  оттуда же. Значит, решение "качать или нет" принимается после одного лёгкого
  JSON-запроса на пакет.
- Токен доступа к файлам короткоживущий и одноразовый для URL; локальный кеш
  от него не зависит.

## Рассмотренные подходы

### A. Проверка локального каталога по `artifactKey` (выбран)

Поток прежний: на каждый пакет уходит runtime-manifest (без файлов). После
валидации манифеста клиент проверяет каталог
`<slug>/<revision>-<artifactKey>/`, маркер завершённой записи и наличие всех
объявленных файлов нужного размера. Если всё сходится — состояние применяется
из кеша, файлы не скачиваются.

Плюсы: минимальная площадь изменений (клиентский GDScript плюс строка в shell),
использует существующие инварианты (`artifactKey`, `prune`, staging/swap),
корректность при переопубликации зависимости сохраняется. Минусы: N лёгких
запросов манифеста при старте; проверка целостности файлов только по размеру,
без хеширования (см. "Что решено здесь").

### B. `artifactKey` в конфиге игры (отклонён)

Прокинуть ключ из бэкенда через `/rooms/:id/game/connection` →
`GameConfigurePayload` → `shell.html.acceptConfig` → GDScript, чтобы решать
всё до сети. Быстрее, но меняет четыре слоя, требует отдавать ключ в момент
соединения (сейчас в статусах только `revision`), а до `WS`-снапшота клиент
может успеть загрузить устаревший ключ. Для текущей задачи выигрыш — минус
несколько мелких запросов, цена — сквозной контракт. Можно добавить поверх A
позже, если запросы манифеста окажутся заметны.

### C. Браузерный blob-кеш (Cache API) (отклонён)

Шелл скачивает файлы JS-ом и складывает по sha256 в Cache Storage, Godot
читает их через мост. Даёт дедуп между ревизиями, но дублирует хранилище с
IDBFS, требует собственной инвалидации и квоты и уводит логику из Godot.
Архитектурно дальше от текущего устройства.

### D. Отдельная база IndexedDB для кеша игры (выбран для хранения)

Игровой shell добавляет второй постоянный каталог `/wired-cache`: Godot
монтирует его как отдельную базу IDBFS, а `packages_root()` на web указывает
туда. Редактор знает только `/userfs`, поэтому его сбросы не могут удалить кеш;
`user://` игры остаётся на месте и ведёт себя как раньше.

Плюсы: полная изоляция, одна строка в shell и одна ветка выбора корня в
`packages_manager.gd`, нативный runtime и smoke-тесты не меняются, откат —
убрать путь из shell. Минусы: путь кеша перестаёт быть `user://` и
становится абсолютным (`/wired-cache/...`), это нужно проверить в браузере; в
профиле появляется вторая база IndexedDB; старый кеш в `user://wired/rooms`
осиротеет.

### E. Оставить общий `/userfs` (отклонён)

Раньше это принималось как best-effort: кеш в общем `/userfs`, редактор может
его стирать, промах превращается в повторную загрузку. Пользователь выбрал
изоляцию, поэтому вариант отброшен.

## Решение (переиспользование A, хранение D)

### Где живёт кеш пакетов

`shell.html` передаёт движку оба постоянных каталога:

```js
engine.startGame({
	persistentPaths: ['/userfs', '/wired-cache'],
	onProgress: function (current, total) { /* как сейчас */ },
});
```

`packages_manager.gd` получает корень хранилища с проверкой, что база реально
смонтирована:

```gdscript
const PACKAGES_ROOT := "user://wired/rooms"
const WEB_CACHE_MOUNT := "/wired-cache"
const WEB_PACKAGES_ROOT := "/wired-cache/wired/rooms"

func storage_root() -> String:
	if OS.has_feature("web") and DirAccess.dir_exists_absolute(WEB_CACHE_MOUNT):
		return WEB_PACKAGES_ROOT
	return PACKAGES_ROOT
```

`packages_root()` и путь slug index строятся от результата; `_slug_index_path()`
берёт `packages_root().get_base_dir()`, чтобы корень решался в одном месте.
Проверка монтирования нужна для отката: если из shell убрать `/wired-cache`,
каталог всё равно создастся в MEMFS (там writable), и без проверки кеш молча
писался бы в непостоянный путь. С проверкой — автоматически возвращаемся в
`user://wired/rooms`. Отдельного test-seam не нужно: на нативной сборке ветка
не срабатывает, а smoke-тест по-прежнему видит `user://wired/rooms/...`.

Абсолютный путь вне `user://` для `FileAccess` и `DirAccess` в проекте уже
используется редакторским web-билдом (`package_fs.gd` пишет по абсолютному
`res://`-пути через `ProjectSettings.globalize_path`), но `ResourceSaver`,
`ResourceLoader.exists/load` и `.import`-sidecar с абсолютным `path=` на этом
пути ещё не проверялись. Это единственное место, которое нельзя доказать
чтением кода: первый ручной шаг должен доказать полный цикл (применение,
`instantiate_scene`, загрузка производных `.res`), иначе изоляция недостижима
без выноса кеша в Cache API/OPFS (вариант C).

Старый кеш в `user://wired/rooms` не мигрирует и не удаляется: редактор,
смонтировавший `/userfs` раньше, всё равно «воскресит» его своим следующим
сбросом. Каталог просто перестаёт читаться и вытесняется браузером по квоте.

### Маркер завершённой записи

В каталоге артефакта появляется файл `.wired-artifact.json`. Он пишется в
`.staging` **после** `AssetDeriver.derive` и **до** `ArtifactStore.swap`,
поэтому ренаме в целевой каталог публикует уже полный артефакт вместе с
маркером. Содержимое:

```json
{
  "formatVersion": 1,
  "packageId": 12,
  "slug": "hero",
  "revision": 7,
  "artifactKey": "9f2c...",
  "totalSize": 123456,
  "fileCount": 42,
  "deriveVersion": 1
}
```

Список файлов в маркере не дублируется: авторитетным остаётся runtime-manifest,
который и так получен до проверки. Маркер отвечает только на вопрос "запись
этого артефакта доведена до конца".

`deriveVersion` — версия клиентского преобразования ассетов (`AssetDeriver`).
`artifactKey` меняется только при публикации на сервере, поэтому изменение
`AssetDeriver` (новое расширение, другой суффикс, другой формат `.import`) само
по себе не инвалидирует кеш. Без этой версии после обновления клиента
пользователь с готовым кешем молча получил бы устаревшие/отсутствующие
`.image.res`/`.audio.res` и не воспроизвёл бы проблему перезагрузкой. Поэтому
`AssetDeriver` получает константу `VERSION`, которую исполнитель поднимает при
любом изменении правил или формата побочных файлов.

### Проверка перед переиспользованием

`ArtifactStore` получает метод вида
`reusable_artifact(package_id, slug, revision, artifact_key, files) -> Dictionary`
(точная сигнатура — на усмотрение исполнителя). Он возвращает пустой словарь,
если каталог нельзя использовать, иначе — данные для применения. Проверки:

1. Каталог `<slug>/<revision>-<artifactKey>/` существует.
2. Маркер существует, парсится, `formatVersion == 1`, `packageId`, `slug`,
   `revision`, `artifactKey` совпадают с запрошенными.
3. Для каждого файла из runtime-manifest файл существует и его размер равен
   объявленному `size`.
4. Для каждого файла артефакта, у которого есть клиентская производная
   (расширение в `AssetDeriver.derivations()`), существуют и производный файл
   (`<filepath><suffix>`), и sidecar (`<filepath>.import`), если сам артефакт
   их не объявляет.

Проверка идёт от манифеста, а не от маркера, поэтому подмена маркера не даёт
доступа к чужим байтам. Хеши на старте не пересчитываются: `artifactKey`
уже гарантирует содержимое, а размер ловит обрыв записи IDBFS. Хеширование
остаётся только на пути скачивания, как сейчас.

Если проверка не прошла, каталог не удаляется: выполняется обычная загрузка
`stage` → `derive` → `swap`, и `swap` заменяет каталог того же ключа через
`.previous`. Так неудачная загрузка оставляет на диске прежний рабочий каталог,
а не пустое место. Отсутствие маркера — это же поведение, поэтому артефакты,
записанные до изменения, просто скачиваются один раз заново.

### Ремонт производных файлов без повторной загрузки

Если основные файлы на месте, но производные отсутствуют (обрыв записи IDBFS)
или `deriveVersion` в маркере отличается от `AssetDeriver.VERSION` (обновился
клиент), каталог не удаляется: `AssetDeriver.derive` вызывается повторно прямо
на существующем каталоге (`staging == final_dir == каталог артефакта`). Это
идемпотентно, sidecar указывает на тот же финальный путь, а при смене версии
перегенерируются все производные, а не только отсутствующие. После успешного
ремонта маркер перезаписывается с текущим `deriveVersion`; если ремонт упал —
каталог удаляется и выполняется обычная загрузка.

Устаревшие производные файлы от прошлых версий правил (например, старый
суффикс) остаются в каталоге, но нигде не объявлены и не используются;
специальная зачистка не нужна.

### Точка входа в переиспользование

Решение принимается в `PackagesManager._sync_package` **после**
`_sync_dependencies` и до `_download_files`. Это важно: к этому моменту
зависимости уже применены (или переиспользованы) на точных ревизиях и ключах
из манифеста, а `slug` и `artifactKey` уже провалидированы. Существующая
проверка "ревизия не старше" в `_sync_package_chain` не меняется.

Ветка переиспользования:

- заполняет `_names`, `_total_bytes` (иначе `_emit_complete` нечего показать);
- собирает `hashes` из `files` манифеста и считает `changed` через
  `_changed_files` относительно `_file_hashes` (после перезагрузки процесса это
  все файлы — ровно как при обычном первом применении);
- публикует `_current_revisions`, `_current_artifact_keys`,
  `_scene_dependencies`, `_file_hashes`, сохраняет slug index;
- вызывает `prune(slug, revision, dir_name)`, чтобы окно ревизий оставалось
  прежним;
- не сбрасывает FS сам: сброс делает вызывающий после пачки применений (см.
  "Durability в браузере");
- возвращает обычный успешный результат с `files` из манифеста и
  диагностическим `"cached": true`.

`package_applied` и `package_progress(complete)` эмитятся существующим кодом
`_sync_package_chain` после возврата результата — отдельных сигналов не нужно.

Следствие: повторный вызов `sync_package` с той же ревизией в том же процессе
тоже перестаёт скачивать файлы. Это корректно, потому что ключ
content-addressed: одинаковый ключ — одинаковые байты. Комментарии в
`_sync_package_chain` про "fresh call must still refresh a changed artifact"
переформулируются: обновление происходит при смене ключа.

### Durability в браузере

`FS.syncfs(false)` не умеет вставать в очередь: если синхронизация уже идёт,
web-загрузчик печатает "Already syncing!" и возвращает resolved promise, то есть
сброс молча пропускается. Поэтому сброс делается не на каждый пакет, а один раз
после пачки применений. `PackagesManager` получает публичный
`flush_storage()`, который `main_scene` вызывает после цикла предзагрузки и
после прохода `_reconcile_client_packages`:

```gdscript
func flush_storage() -> void:
	if not OS.has_feature("web"):
		return
	JavaScriptBridge.force_fs_sync()
```

Это тот же приём, что в `addons/wired_bridge/plugin.gd`. Без сброса свежая
запись маркера/файлов и удаления `prune` могут не дожить до следующей
перезагрузки: IDBFS не синхронизируется на каждую запись. `FS.syncfs(false)`
синхронизирует все смонтированные базы этого инстанса (`/userfs` и
`/wired-cache`), отдельного вызова на базу не нужно. Штатный выход из игры FS
тоже сбрасывает (`GodotOS.finish_async` → `GodotFS.sync`), а вызов после пачки
закрывает окно при закрытии вкладки и переключении страниц.

### Совместимость и откат

- Сервер, `packages/shared`, API и фронтенд не меняются. Меняются shell-шаблон
  игры (`_wired/web/shell.html`) и клиентский GDScript; из shell пересобирается
  export (`pnpm export:game`).
- Старые каталоги без маркера не используются и перезаписываются штатным
  `swap` при первой загрузке; каталоги старого web-кеша в `user://wired/rooms`
  больше не читаются.
- Отключение кеша — константа в `packages_manager.gd` (например
  `const CACHE_REUSE := true`); отключение изоляции — убрать `/wired-cache` из
  `persistentPaths` в shell: проверка монтирования сама вернёт корень
  `user://wired/rooms`, правок GDScript не нужно.
- Нативный runtime получает то же ускорение при рестарте процесса: там корень
  прежний `user://` и логика общая.

## Что решено здесь (мои решения, не требования пользователя)

- Проверять целостность по размеру, не по sha256: ключ уже content-addressed,
  а полное хеширование на старте съело бы выигрыш. Если появится требование
  "защита от порчи IDBFS", хеши можно включить отдельным флагом.
- Маркер хранит только метаданные, список файлов берётся из манифеста.
- Проверка и переиспользование — после синхронизации зависимостей, а не до.
- Отдельная версия клиентского преобразования (`deriveVersion`) и проверка
  производных файлов: иначе обновление `AssetDeriver` не доедет до кеша.
- Кеш-промах не удаляет каталог сам: обычный `swap` заменяет каталог того же
  ключа, поэтому провал загрузки не уничтожает рабочий артефакт.
- Никаких новых лимитов объёма: установившийся объём не растёт относительно
  текущего поведения.
- Кеш пакетов вынесен в отдельную базу `/wired-cache`, а не оставлен в общем
  `/userfs`: иначе редактор стирает его своими сбросами.
- Корень выбирается по факту монтирования `/wired-cache`, а не только по
  `OS.has_feature("web")`: иначе откат через shell писал бы кеш в MEMFS.
- Старый кеш в `user://wired/rooms` не переносится и не удаляется (редактор
  воскресил бы его своим сбросом); остальные данные `user://` остаются в
  `/userfs`.
- Сброс FS — один раз на пачку применений через `flush_storage()`, потому что
  `force_fs_sync` не умеет вставать в очередь.

## Что остаётся исполнителю

- Точные имена методов/констант и место хранения маркера внутри
  `ArtifactStore` vs `PackagesManager`; имя константы `AssetDeriver.VERSION`.
- Вспомогательный метод `AssetDeriver` для списка ожидаемых производных файлов
  (чтобы проверка и `derive` не расходились в правилах).
- Формат диагностического лога (в духе `WIRED_PACKAGES_APPLIED`), например
  `WIRED_PACKAGES_CACHED package=%d revision=%d artifact=%s`.

## Проверка

Headless smoke-тест `packages/server/godot_project/_wired/tests/packages_manager_smoke.gd`
(фикстуры без сети через `request_override`) расширяется:

1. **Перезагрузка**: применить пакет, создать новый `PackagesManager` с той же
   комнатой и транспортом, который падает/считает вызовы. Второй `sync_package`
   с тем же `artifactKey` не делает ни одного запроса `runtime-files`, состояние
   и slug index заполнены, `changed_files` описывает все файлы.
2. **Битый кеш**: удалить/укоротить один файл артефакта или маркер → следует
   обычная загрузка, артефакт восстанавливается.
3. **Смена ключа**: переопубликовать зависимость (новый `artifactKey`) →
   каталог другой, файлы скачиваются, старый каталог вычищается `prune`.
4. **Старые артефакты**: каталог без маркера не используется и заменяется.
5. **Производные файлы**: удалить `.image.res` при валидном маркере → каталог
   переиспользуется, файл пересоздаётся без загрузки; поднять
   `AssetDeriver.VERSION` → производные перегенерируются, загрузки нет.
6. **Окно ревизий**: после переиспользования на диске остаются применённая и
   предыдущая ревизии, как сейчас.
7. **Корень хранилища**: `packages_root()` и `_slug_index_path()` используют
   один корень; на нативной сборке это `user://wired/rooms`, slug index лежит
   рядом. Web-ветка (`/wired-cache`) проверяется вручную.

Фикстура должна считать ключ зависящим от байтов пакета (как серверный
`commitSha`), иначе сценарий "те же байты под тем же ключом" нельзя смоделировать
честно. Существующий `_test_same_revision_refresh` обновляется под новую
семантику: одинаковый ключ — без загрузки, изменённые байты — новый ключ.

Ручная проверка (браузер, `pnpm export:game`, запущенный backend):

1. Открыть Game tab, дождаться применения пакетов и появления сцены: это
   доказывает, что `ResourceSaver`/`ResourceLoader` и `.import` с абсолютным
   `path=` работают вне `user://`. В DevTools → Application → IndexedDB должно
   быть две базы (`/userfs` и `/wired-cache`), файлы пакетов — в `/wired-cache`.
   Если второй базы нет, `persistentPaths` не доехал (загрузчик молча игнорирует
   неизвестные ключи) — смотреть `shell.html`.
2. Перезагрузить страницу: в Network нет запросов `runtime-files`, игра
   работает.
3. Не закрывая страницу, открыть редактор, создать и удалить пакет (это
   заставляет редактор сделать `force_fs_sync`), вернуться в Game tab и
   перезагрузить страницу: запросов `runtime-files` по-прежнему нет. Это и есть
   проверка изоляции.
4. Переопубликовать зависимость: новый `artifactKey`, полная загрузка, старый
   каталог вычищается.

Команда smoke-теста (нужен локальный Godot 4.8-beta2):

```bash
godot --headless --path packages/server/godot_project/_wired \
  --script res://tests/packages_manager_smoke.gd --quit-after 600
```

Ожидаемый вывод: `PACKAGES_MANAGER_SMOKE_OK`.

## Риски

- **Остальной `user://` игры по-прежнему общий с редактором.** Перенесён только
  кеш пакетов; настройки, логи и `state.json` клиента остаются в `/userfs` и
  могут быть откачены сбросом редактора (и наоборот). Это прежнее поведение,
  пакетов оно не касается.
- **Абсолютный путь `/wired-cache`.** `stage`/`swap`/`derive` пишут в этот же
  корень, поэтому отказ движка писать вне `user://` — не кеш-промах, а
  невозможность применить пакет. Проверяется первым ручным шагом (полный цикл);
  если не сработает, изоляция достигается только через Cache API/OPFS
  (вариант C).
- **Абсолютный `path=` в `.import`-sidecar.** Раньше там был `user://`, теперь
  `/wired-cache/...`. Это проверяет тот же ручной шаг; на нативном runtime путь
  остаётся прежним.
- **Сброс FS может быть пропущен.** `force_fs_sync` при занятой синхронизации
  молча ничего не делает; поэтому сброс один на пачку, а не на пакет. Худшее
  последствие — потеря последних записей при закрытии вкладки, то есть
  кеш-промах в следующий раз.
- **Две вкладки игры одной комнаты**: обе пишут в одну базу `/wired-cache` —
  побеждает последний писатель. Маркер и проверка размеров превращают это в
  кеш-промах и повторную загрузку, данные игры не страдают.
- **Квота браузера**: при нехватке места IndexedDB может вытеснить данные;
  это тоже кеш-промах. Ошибки записи обрабатываются существующим путём отказа
  применения (как сейчас при переполнении).
- **Кратковременная неконсистентность маркера**: маркер пишется до `swap`,
  поэтому видимый каталог либо без маркера, либо полный; `force_fs_sync` после
  применения закрывает окно до перезагрузки.
