# Кеширование с ревалидацией для Godot-редактора и базового проекта

Дата: 2026-11-14
Статус: одобрено

## Зачем

Ассеты веб-редактора (`/api/godot-editor/*`: `godot.editor.wasm` ≈ 67 МБ,
`godot.editor.js`, шрифты, ворклеты) и файлы базового проекта
(`/api/godot-project/wired/*`: 128 файлов, ≈ 725 КБ) отдаются контроллером
`GodotEditorProviderController` без кеш-заголовков — браузер их не хранит и
качает заново при каждом открытии редактора. Механизм ревалидации уже есть в
`src/common/static-assets.ts` (ETag size+mtime, `Cache-Control: no-cache`,
304 на `If-None-Match`) и включён только у контроллера game-export, который
ходит через тот же `/api`-рерайт — то есть схема уже проверена end-to-end.

## Цели

- Ассеты редактора и файлы базового проекта получают `ETag` +
  `Cache-Control: no-cache` и отвечают 304 на `If-None-Match`.
- Повторное открытие редактора: wasm идёт из HTTP-кеша браузера, по сети
  ходят только валидаторы; базовый проект — 128 маленьких 304-ов вместо
  полной перекачки.
- HTML-оболочка редактора (`godot.editor.html`) остаётся `no-store` — как
  у game-export, чтобы перезалитое дерево подхватывалось сразу.
- Поведение game-export не меняется.

## Не-цели

- Сжатие (gzip/brotli) — отдельная задача, сильнее всего влияет на первую
  загрузку.
- Версионированные URL, `max-age`/immutable — не нужны для 304-схемы.
- Клиентские изменения: стирание FS редактора при перезагрузке страницы
  (изоляция комнат), `downloadProject`, манифест `ProjectInfo` — не трогаем.
- Манифест `/godot-project/wired` не кешируется: это пара килобайт JSON.

## Anti-goals

- Нельзя допустить расхождения `godot.editor.js` и `godot.editor.wasm`:
  редактор валидируется при каждом запросе (no-cache), а не живёт на
  «вере в свежесть».
- Нельзя ставить `no-store` файлам базового проекта: это payload для
  файловой системы редактора, каждый из них должен уметь отвечать 304.

## Ограничения

- ETag — size+mtime файла на диске (общая функция `serveStaticAsset`).
  Ассеты редактора перезаливаются только `pnpm fetch:editor` (пinned
  4.8-beta2), файлы `_wired` меняются только с релизом — расхождение
  кеша с диском на практике не возникает.
- Для файлов проекта `crossOriginIsolation: false` и
  `application/octet-stream` остаются как есть; опции лишь добавляют
  ETag/Cache-Control.

## Подходы

**A. Включить существующие флаги — выбран.**

`getEditorFile` → `{ revalidate: true, noStoreShell: true }`;
`getGodotProjectFile` → `{ revalidate: true }` (у дерева проекта нет
«оболочки» — html внутри `_wired` остаётся обычным payload-файлом).
Патч на два вызова плюс тесты. Минус: один валидационный запрос на файл —
принимаем, файлы единицы, а HTTP/2 делает 304-ы дешёвыми.

**B. `max-age`/immutable и версионированные URL — отклонено.**

Базовый проект меняется только с релизами, и `max-age` избавил бы от
128 валидаций. Но ассеты редактора обязаны валидироваться всегда
(см. Anti-goals), а версионирование URL — изменение маршрута ради
маргинальной экономии поверх 304. Оставлено на потом, если валидации
окажутся заметны.

**C. Сжатие — отклонено в этом объёме.**

Самый большой выигрыш на первой загрузке (wasm ~67 → ~20–25 МБ), но это
настройка nginx/бэкенда с CPU-ценой; отдельная задача.

## Как это устроено

- Оба метода контроллера передают опции в существующую
  `serveStaticAsset`; логика 304/ETag уже там и покрыта тестами
  game-export.
- Тесты `godot-editor-provider.controller.spec.ts` (в supertest-блоке
  «HTTP wildcard routing», по образцу game-export):
  - ассет редактора: `cache-control: no-cache`, `etag` определён,
    повторный запрос с `If-None-Match` → 304, включая форму
    `W/"...", "stale"`;
  - `godot.editor.html`: `cache-control: no-store`;
  - файл проекта: `no-cache` + 304; `project.godot` продолжает
    отдаваться как раньше.

## Проверка

- `pnpm --filter server exec jest godot-editor-provider`
- `pnpm --filter server test`, `pnpm --filter server check-types`,
  `pnpm --filter server lint`
- Вручную: открыть редактор дважды — в Network у wasm/js/файлов проекта
  304 или «из кеша», повторная загрузка без перекачки 67 МБ.
