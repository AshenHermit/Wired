# Этап 4. Хранение пакетов и пофайловая загрузка — результаты

Дата: 2026-10-29. Ветка: `working-on-godot-rooms`.
Статус: критерий готовности выполнен.

## Итог

Пакет из нескольких файлов загружается на backend по HTTP, публикуется как
неизменяемая ревизия, а игровой сервер Godot и браузерный редактор получают
те же файлы без архива. Файлы вне каталога пакета не изменяются: и backend,
и Godot-загрузчик, и frontend работают только внутри управляемого каталога.

## Формат пакета

Манифест ревизии (ответ `GET /scripting-packages/:id/manifest`):

```json
{
  "packageId": 10,
  "name": "Stage 4 smoke revisions",
  "revision": 2,
  "files": [
    { "filepath": "scripts/main.gd", "size": 29, "sha256": "9a40…e079" }
  ],
  "totalSize": 29,
  "publishedAt": "2026-10-29T00:41:12.000Z"
}
```

Типы лежат в `packages/shared/src/api/types.ts`: `PackageFileEntry`,
`PackageRevisionStatus`, `PackageRevision`, `PackageManifest`,
`CreatePackageRevisionPayload`. В манифесте только относительные POSIX-пути,
размер в байтах и `sha256` в нижнем регистре; архива нет — каждый файл
передаётся отдельным запросом.

## API

| Метод и путь | Доступ | Назначение |
| --- | --- | --- |
| `POST /scripting-packages/:id/revisions` | JWT + право редактирования | создать черновик ревизии с объявленным списком файлов |
| `POST /scripting-packages/:id/revisions/:rev/files/*path` | JWT + право редактирования | загрузить один файл черновика (multipart, поле `file`) |
| `POST /scripting-packages/:id/revisions/:rev/publish` | JWT + право редактирования | проверить и опубликовать ревизию |
| `GET /scripting-packages/:id/revisions` | публично | список опубликованных ревизий, новые сверху |
| `GET /scripting-packages/:id/manifest` | публично | последняя опубликованная ревизия |
| `GET /scripting-packages/:id/revisions/:rev/manifest` | публично | манифест конкретной опубликованной ревизии |
| `GET /scripting-packages/:id/revisions/:rev/files/*path` | публично | файл опубликованной ревизии |

Публикация идемпотентна: повторный `publish` уже опубликованной ревизии
возвращает её описание и не трогает диск.

Статусы ревизии: `draft`, `published`, `discarded`. Вытесненный черновик
не удаляется из БД, а помечается `discarded`: номера ревизий не
переиспользуются, поэтому старая сессия редактирования не может
опубликовать чужие файлы. Публичный список отдаёт только `published`;
черновики доступны лишь при явном запросе из редактора (`includeDrafts`).
Пока пакет публикуется, загрузка файлов в него отклоняется (`409`), а
`publish` проверяет контрольные суммы ещё раз уже после переименования —
отдаются ровно те байты, которые прошли проверку.

## Хранилище

Метаданные — новая таблица `scripting_package_revision` (сущность
`ScriptingPackageRevision`, уникальный индекс `package + revision`).
Существующая таблица пакетов и её колонки не менялись; при `DB_SYNC=1`
добавляется только новая таблица.

Файлы в `STORAGE_DIR/PACKAGES_FILES_DIR`:

```
<root>/<packageId>/<filepath>              # старый CRUD, не тронут
<root>/<packageId>/drafts/<revision>/…     # черновик, можно перезаписать
<root>/<packageId>/revisions/<revision>/…  # опубликованная ревизия, неизменяема
```

Правила:

- черновик не виден игре и клиентам: отдаются только опубликованные ревизии;
- публикация проверяет, что набор файлов на диске совпадает с объявленным
  манифестом (нет пропущенных и лишних), затем размер и `sha256` каждого
  файла; частичная загрузка публикацию не проходит;
- после проверки каталог черновика переименовывается в `revisions/<revision>`;
  если запись в БД не удалась, выполняется обратное переименование, поэтому
  последняя корректная опубликованная версия остаётся на месте;
- опубликованная ревизия не перезаписывается (`409`);
- новый черновик пакета вытесняет неопубликованные черновики этого пакета.

Валидация путей (`package-path.ts`) запрещает абсолютные пути, диски,
`~`, `\`, пустые сегменты, `.` и `..`, управляющие символы, сегменты длиннее
255 байт и пути длиннее 1024 байт; дубликаты путей без учёта регистра
отклоняются. Старые маршруты `:id/files/*path` используют ту же проверку и
дополнительно запрещают служебные каталоги `drafts` и `revisions`, чтобы
через legacy API нельзя было прочитать черновик или опубликованную ревизию
в обход манифеста.

Лимиты манифеста: не более 2000 файлов, 64 МиБ на файл, 256 МиБ на ревизию.

## Godot-проект

`_wired/scripts/global/packages_manager.gd` (`class_name PackagesManager`)
загружает опубликованную ревизию и раскладывает её в

```
user://wired/packages/<packageId>/<revision>/<filepath>
```

Порядок работы `sync_package(package_id)`:

1. `GET /scripting-packages/:id/manifest`; пустой ответ или `404` — у пакета
   нет опубликованной ревизии;
2. каждый файл скачивается в память, проверяются относительный путь, размер и
   `sha256`;
3. всё пишется в `<packageId>/.staging/`, затем каталог переименовывается в
   `<packageId>/<revision>/`; предыдущая ревизия сначала уходит в
   `<packageId>/.previous/` и удаляется только после успешной замены;
4. каталоги других ревизий этого же пакета удаляются — только внутри
   `user://wired/packages/<packageId>/`.

Ошибка на любом шаге оставляет предыдущую ревизию нетронутой (в том числе
сбой переименования при замене); в лог пишется `WIRED_PACKAGES_SYNC_FAILED`,
сигналы — `package_applied` / `package_failed`. Ошибка сети не выдаётся за
«нет опубликованной ревизии»: `404` и сбой транспорта различаются.

Адрес API берётся из аргумента `--api-url`, переменной окружения
`WIRED_API_URL` или по умолчанию `http://127.0.0.1:3000`. Backend передаёт
`--api-url` при запуске процесса комнаты (`PORT` процесса API). `main_scene.gd`
создаёт менеджер при старте в обоих режимах и печатает
`WIRED_PACKAGES_READY api=…`. Синхронизация пакетов по событию публикации
подключается на этапе 5; сейчас `get_packages_manager()` доступен вызывающей
стороне.

## Frontend

- `frontend/src/app/room/[room_code]/(godot)/godot-packages-fs.ts` — типизированная
  обёртка над `window.editor.editor.rtenv.FS` кастомной сборки. Каталог
  пакета — `<rootPath>/<project>/packages/<packageId>/`, где `rootPath`
  редактора `/home/web_user`; чтение, запись, рекурсивный список, удаление,
  сбор файлов с `sha256`, замена содержимого целиком и `sync` (IndexedDB).
  Файлы-метаданные редактора (`*.uid`, `*.import`, точечные каталоги) не
  публикуются и не удаляются.
- `package-sync.ts` — `publishPackageFiles` (собрать файлы из FS, создать
  черновик, загрузить по одному, сверить `sha256` из ответа сервера,
  опубликовать) и `syncPackageRevision` (получить манифест, скачать файлы,
  сверить и записать в FS).
- `use-package-files.ts` — единственная точка доступа UI к экземпляру
  редактора; компоненты не обращаются к `window.editor` напрямую.
- `frontend/src/utils/sha256.ts` — SHA-256 через Web Crypto.

Перед записью проверяются все файлы, поэтому повреждённая загрузка не
заменяет уже лежащую в FS версию. Запись идёт в `packages/.<id>.staging`,
затем каталог пакета заменяется через `.<id>.previous`: сбой посередине не
оставляет смесь двух ревизий, а метаданные редактора переносятся в новую
версию.

## Ограничения и что осталось

- Признак «опубликовано» выставляется по успешной проверке и переименованию;
  отдельного подтверждения от Godot-runtime на этом этапе нет — это этап 5.
- Уведомления о новой ревизии нет: frontend и Godot загружают манифест по
  требованию (`syncPackageRevision`, `sync_package`). Канал событий Emit —
  этап 5.
- Открытый редактор Godot может не перечитать файлы, записанные в FS
  снаружи: изменения появляются после пересканирования файловой системы
  редактором (`Scan` / переоткрытие проекта). Перезагрузка страницы не нужна,
  но автоматическое обновление дерева файлов — задача этапа 5–6.
- Каталог пакета в редакторе (`packages/<id>/`) и каталог в игре
  (`user://wired/packages/<id>/<rev>/`) разные: игра получает файлы по HTTP,
  а не из виртуальной FS редактора.
- Права на редактирование пакета остаются упрощёнными: для пакета комнаты
  допускается любой аутентифицированный пользователь (существующее правило
  `assertPackageEditing`); точка будущей проверки прав — в сервисе.
