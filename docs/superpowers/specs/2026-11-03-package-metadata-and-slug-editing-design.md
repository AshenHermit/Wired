# Редактирование пакета: slug, метаданные и отказ от tombstone

Дата: 2026-11-03
Статус: proposal

Дополняет и частично отменяет:
`2026-11-02-package-slug-design.md` (правила tombstone),
`2026-11-03-package-workshop-design.md` (редактирование метаданных в панели публикации, запрет переиспользования slug).

## 1. Контекст

Три связанные проблемы, всплывшие при ручной проверке workshop:

1. **Slug нельзя изменить.** `id` — идентичность, `slug` — имя папки в редакторе и в рантайме; `UpdateScriptingPackageDto` не содержит поля `slug`, `ScriptingPackagesService.update` его не присваивает. Опечатка в slug (кейс `example_package`) лечится только удалением пакета.
2. **Удалённые workshop-slug заблокированы навсегда.** `remove()` пишет `RetiredPackageSlug`, `insertPackage` для глобальной области бросает `409 slug_retired`, а `checkSlugAvailability` возвращает `reason: 'retired'`. Пользователь создал приватный пакет `example_package` (room-scope tombstone не проверяет — поэтому создание прошло), а публикация в workshop упала ровно на этой проверке.
3. **Метаданные редактируются в панели публикации.** Имя, версия, описание и теги правятся в диалоге «Опубликовать в workshop», хотя это свойства пакета комнаты, а не операции публикации; имя и версия дополнительно правятся карандашами на карточке. Два разных места для одного и того же.

Решения пользователя:

- разрешить переиспользование удалённых workshop-slug;
- разрешить редактировать slug **в любой момент**, с переписыванием (`@45@`: «В любой момент, с переписыванием»);
- вынести редактирование информации о пакете из панели публикации в отдельную панель по кнопке в more-меню (`@19@`).

## 2. Goals

- Пользователь может изменить slug пакета комнаты в любой момент; сервер и редактор остаются согласованными.
- Удалённый workshop-slug можно использовать снова; тупик `slug_retired` исчезает из API и UI.
- Все метаданные пакета (имя, версия, slug, описание, теги) правятся в одном месте — диалоге «Редактировать пакет» из more-меню карточки.
- Публикация в workshop — подтверждение с предпросмотром, без редактирования метаданных.

## 3. Non-goals

- Каскадное переименование workshop-записи при переименовании пакета комнаты.
- Переписывание локальных копий зависимых пакетов в чужих редакторах (серверные published-копии переписываются, см. §7.4).
- Удаление таблицы `retired_package_slug` из БД автоматически (политика «без миграций»).
- Уборка осиротевших папок `packages/<old>` в рантайме комнаты и старых артефактов на диске сверх описанного ниже.
- Переименование slug у draft-ревизий, которых нет на сервере.
- Переименование глобальных workshop-записей через PATCH (см. §7.3).

## 4. Anti-goals

- Переименование, при котором сервер и папка в редакторе расходятся (пакет «пропадает» из панели).
- Тихо ломающиеся зависимости: переименование без предупреждения о пакетах, которые ссылаются на старый slug.
- Второй источник правды для метаданных (карточка + панель публикации + диалог редактирования).

## 5. Constraints

- `DB_SYNC=1`, миграций нет. Схема меняется сама при старте; TypeORM 0.3.28 не удаляет таблицы, поэтому `retired_package_slug` останется сиротой (безвредно).
- Потребители проверяют `size`/`sha256` против манифеста: редактор (`godot-packages-fs.ts`), синхронизация (`package-sync.ts`), рантайм (`packages_manager.gd`). Любое переписывание обязано обновить `scripting_package_revision.files`.
- `artifactKey` зависит только от `(packageId, revision)` — при переписывании той же ревизии ключ не меняется, значит старый артефакт обязан быть удалён, иначе будет отдан устаревший контент.
- `PackageClosureResolver.fileBytes` кеширует байты в памяти без инвалидации — нужен сброс.
- У моста редактора нет операции rename; `collect`/`replace` теряют `.uid`/`.import` (пересоздание uid ломает `uid://`-ссылки), поэтому переименование папки должно быть отдельной операцией в GDScript.
- Копия UI и документации — на русском; идентификаторы — на английском.

## 6. Approaches

### 6.1. Когда разрешено менять slug

| Вариант | Что даёт | Чем платим |
|---|---|---|
| A. Только до первой публикации | Дешево: ни переписывания, ни артефактов | Не решает исходный кейс: `example_package` уже опубликован |
| **B. В любой момент, с переписыванием** (выбрано) | Один slug на всю жизнь пакета, кейс пользователя закрыт | Сервер переписывает ревизии, чистит артефакты, редактор переименовывает папку |
| C. Slug как отображаемое имя, папка остаётся старой | Ничего переписывать не надо | Две идентичности, ссылки `res://packages/<slug>/` перестают совпадать с папкой — отвергнуто |

### 6.2. Где редактируются метаданные

| Вариант | Что даёт | Чем платим |
|---|---|---|
| A. Карандаши на карточке (как сейчас для имени/версии) | Быстро | Нет места для slug/описания/тегов, карточка перегружена |
| **B. Отдельный диалог «Редактировать пакет» из more-меню** (выбрано) | Одна форма на все поля, карточка только читает | +1 диалог |
| C. Как сейчас: в панели публикации | Ничего нового | Смешивает свойства пакета с действием публикации — то, что просили убрать |

### 6.3. Что делать с tombstone

| Вариант | Что даёт | Чем платим |
|---|---|---|
| A. Оставить сущность, убрать проверки | Минимум диффа | Мёртвый код и мёртвая таблица в репозитории |
| **B. Удалить сущность, проверки и код ошибки** (выбрано) | Один источник правды: живой slug | Сиротская таблица в БД (не удаляется без ручного SQL) |
| C. Удалить таблицу через `DB_SYNC` | Чистая схема | Невозможно: TypeORM не дропает таблицы |

## 7. Design

### 7.1. Slug: уникальность без tombstone

- `RetiredPackageSlug` удаляется целиком: entity-файл, регистрация в `scripting-packages.module.ts`, `godot-game.module.ts`, `entities.metadata.spec.ts`, инъекция репозитория, проверка в `insertPackage`, запись в `remove()`, опция `{ tombstone }` у `remove()` и `rollbackCreatedPackage`.
- `remove(id)` снова без опций. `package-workshop.service.ts` вызывает его без флагов при откате созданной записи.
- `PackageSlugAvailability.reason` сужается до `'taken'`; `global` имеет тот же суженный тип. Одинаково в сервере и фронтенде (тип по-прежнему дублируется, в shared не переезжает — как и раньше).
- Код ошибки `slug_retired` исчезает из API и из `workshopErrorMessage`.
- `SlugCheckState` теряет `'retired'`, `SLUG_HINT.retired` удаляется.
- Создание пакета комнаты по-прежнему проверяет только область комнаты: глобальный slug может быть занят — пакет приватный, публикация предложит fork. Дополнительно в диалоге создания показывается неблокирующая подсказка, если `global.available === false`: «Slug занят в workshop — при публикации будет предложен fork».
- **Защита от осиротевшей папки.** Раз slug можно переиспользовать, при создании пакета проверяем локальную папку: если `files.exists(slug)` и `snapshot` непустой — ошибка `slug_dir_exists` («В редакторе уже есть папка с этим slug; переименуйте или удалите её»). Пустая папка переиспользуется как раньше. Это **проверка только на клиенте** (сервер не знает про FS редактора), поэтому живёт в UI-слое и не входит в коды ошибок API.
- Таблица `retired_package_slug` остаётся в БД как сирота. Ручной `DROP TABLE IF EXISTS retired_package_slug;` — вне задачи, выполняется отдельно на общей/прод-БД.

### 7.2. Диалог «Редактировать пакет»

Открывается из more-меню карточки пунктом «Редактировать пакет» (над «Опубликовать в workshop»). Одна форма на пять полей:

| Поле | Правила |
|---|---|
| Имя | trim, непустое (`package_metadata_empty`) |
| Версия | trim, непустая; правила как у текущего карандаша версии |
| Slug | `^[a-z0-9_]{1,64}$`, минимум одна буква (`SLUG_PATTERN`/`normalizeSlug`); проверка доступности с `excludeId` |
| Описание | свободный текст, trim, может быть пустым, лимит как у сервера |
| Теги | разбор как в текущей панели публикации (`parseTags`), ошибки `invalid_tags` |

Поведение:

- Сохранение — один `PATCH /scripting-packages/:id`. Права — существующий `assertPackageEditing` (PATCH/DELETE), т.е. уже́ уже, чем публикация.
- Изменённый slug валидируется debounce-ом через `GET /scripting-packages/slug-availability?slug=&roomId=&excludeId=`; текущий slug считается валидным без запроса.
- Если сервер вернул `409 slug_in_use_by_dependents`, диалог показывает список пакетов, ссылки в которых будут обновлены, и кнопку «Переименовать и обновить ссылки», которая повторяет PATCH с `confirmSlugRename: true`.
- Карточка становится только для чтения: имя, версия, slug, описание и теги отображаются, карандаши `MetadataField` удаляются.
- Панель публикации (`WorkshopPublishDialog`) превращается в предпросмотр: имя, slug, версия, описание, теги — только чтение, кнопка «Опубликовать». Никаких полей ввода и никакого prefill: `getScriptingPackage` остаётся только для чтения описания и тегов в предпросмотре, значения из ответа никуда не подставляются и в PATCH/POST не уходят.
- `POST /:id/workshop` вызывается без метаданных: сервер берёт `name/version/description/tags` из пакета комнаты (текущая ветка `metadata ?? pkg.*`). DTO остаётся с необязательными полями для совместимости.

### 7.3. API

`PATCH /scripting-packages/:id` (существующий, `UseAuthGuard` + `assertPackageEditing`):

```ts
type UpdateScriptingPackageDto = {
  // ...существующие поля
  slug?: string;              // новое: переименование
  confirmSlugRename?: boolean; // новое: согласие на переименование с зависимостями
};
```

`UpdateScriptingPackagePayload` в `packages/shared/src/api/types.ts` получает те же два поля.

`GET /scripting-packages/slug-availability` получает необязательный `excludeId: number` (пакет, который не считается занявшим slug).

Ошибки переименования:

| Код | HTTP | Когда | Что в теле |
|---|---|---|---|
| `invalid_slug` | 400 | slug не прошёл `normalizeSlug` | `message` |
| `slug_taken` | 409 | slug занят в области пакета (комната) | `message` |
| `slug_in_use_by_dependents` | 409 | на пакет ссылаются опубликованные пакеты, `confirmSlugRename` не передан | `dependents: [{ packageId, name }]` |
| `slug_not_editable` | 400 | пакет глобальный (workshop-запись) | `message` |
| `slug_rewrite_failed` | 500 | не удалось переписать байты или откатить | `message`, в логе — детали |

`slug_in_use_by_dependents` возвращается с `reason: 'dependents'`, чтобы фронтенд мог отличить его от прочих 409 без разбора текста.

Смешанный PATCH атомарен: сначала валидируется и выполняется переименование, затем в **той же транзакции** применяются остальные поля. При любом 409/500 из переименования не сохраняется ничего, и диалог повторяет всю форму целиком (включая `confirmSlugRename`).

### 7.4. Серверное переименование

`ScriptingPackagesService.update` при `dto.slug !== undefined && dto.slug !== pkg.slug` делегирует в новый приватный `renameSlug(id, nextSlug, confirm)`; остальные поля применяются как раньше. Если slug не изменился — обычный путь.

Алгоритм:

1. `normalizeSlug(nextSlug)`; ранний выход, если совпадает.
2. Переименовывать можно только пакет комнаты: `pkg.roomId === null` → `400 slug_not_editable` (slug workshop-записи меняется только созданием новой записи).
3. Вычислить `scopeKey` (`room:<id>`); взять advisory-локи на `package_slug:<scope>:<oldSlug>` и `package_slug:<scope>:<newSlug>` **в лексикографическом порядке ключей** (детерминированный порядок исключает дедлок между встречными переименованиями).
4. Проверить, что `newSlug` свободен в этой области, исключая сам пакет (`slug_taken`).
5. `dependents = delivery.findDependentRoomPackages(id)` — транзитивное замыкание зависимых **этой же комнаты**. Если список непуст и `confirmSlugRename !== true` — `409 slug_in_use_by_dependents` с `{packageId, name}` (имена из БД, без обращения к другим комнатам).
6. Взять блокировки публикации `wired.package-publish:<id>` для `[id, ...dependents.packageId]` в порядке возрастания id (см. §7.4.1) и помешать публикации/загрузкам на это время.
7. Собрать план переписывания (`res://packages/<old>/` → `res://packages/<new>/` для `.gd/.tscn/.tres/.import`, whole-slug, как `rewriteForkSlug`):
   - сам пакет — все опубликованные ревизии и все его draft-ревизии;
   - каждый зависимый — только опубликованные ревизии (его ссылка на переименованный пакет должна остаться рабочей, иначе комната тихо сломается, а rebuild артефакта упадёт с `package_dependency_unknown_slug`).
8. Подготовить деревья: `<revision>.rewrite` рядом с `<revision>`, скопировать файлы, заменить байты, посчитать sha256; получить новые `{filepath,size,sha256}` для каждой ревизии.
9. Свап: `<revision>` → `<revision>.old`, `<revision>.rewrite` → `<revision>`; `.old` держим до коммита.
10. В одной транзакции: `scripting_package.slug = newSlug` и `files` каждой переписанной ревизии (в том числе ревизий зависимых пакетов).
11. После коммита: удалить `.old`-деревья, `delivery.invalidatePackage(id)` для каждого переписанного пакета (сбрасывает кеш резолвера и удаляет артефакты), освободить блокировки и оповестить рантаймы (`PackageSyncService`: сброс состояния по переписанным пакетам, включая сам переименованный, — не `dispatchOwnRevision`, который пропускает ту же ревизию).
12. Любая ошибка до шага 10 — восстановить `.old` обратно, удалить `.rewrite`, освободить блокировки, вернуть `slug_rewrite_failed`; после шага 10 ошибки уборки только логируются.

Зависимые пакеты переписываются только в серверных published-байтах. Их копии в редакторе у авторов остаются со старым slug и будут возвращать старое имя при следующей публикации — это осознанный остаточный риск (§9): сервер не может править чужой браузер.

### 7.4.1. Сериализация с публикацией

Переименование двигает те же деревья ревизий, что и `publish()`, поэтому обязано использовать ту же защиту: advisory-лок `wired.package-publish:<id>` и in-process набор `publishing` (он же блокирует uploads через `assertNotPublishing`).

- Защита выносится в отдельный провайдер `PackagePublishLockService` (`package-publish-lock.service.ts`): публичный `runWithPublishLocks(packageIds: number[], fn)` берёт локи в порядке возрастания id (детерминированно, без дедлоков между переименованиями), помечает все id как `publishing`, выполняет `fn`, снимает локи в обратном порядке, и публичный `assertNotPublishing(packageId)`. Отдельный провайдер, а не метод `PackageRevisionsService`, потому что `ScriptingPackagesService` уже импортируется в `PackageRevisionsService` — прямая инъекция дала бы цикл. `PackageRevisionsService.publish` переводится на этот провайдер без изменения поведения. Отсутствие DataSource — как у публикации: только in-process защита.
- Переименование выполняется внутри `runWithPublishLocks([id, ...dependents])`.
- Неполные draft'ы (файлы объявлены, но ещё не загружены) не мешают: переписываются только реально существующие файлы, а `files`-колонка draft-ревизии не меняется. Загрузка, пришедшая после переименования, увидит новую папку только после переименования в редакторе (клиент делает его сразу после PATCH).

Новые/изменённые методы:

- `PackageStorageService` — три фазы, чтобы одна транзакция могла покрыть ревизии нескольких пакетов:
  - `rewriteRevision(packageId, revision, kind: 'published' | 'draft', transform): Promise<PackageFileEntry[] | null>` — готовит `<revision>.rewrite`, свапает её на место `<revision>`, оставляя `<revision>.old`; `null`, если директории ревизии нет на диске (объявленный, но не загруженный draft);
  - `finishRewrite(packageId, revision, kind)` — удаляет `.old` после коммита;
  - `abortRewrite(packageId, revision, kind)` — возвращает `.old` на место и удаляет `.rewrite`.
  Публичные, чтобы сервис переименования не трогал диск напрямую. Одна транзакция (шаг 10) охватывает ревизии нескольких пакетов, поэтому commit не может быть колбэком одной ревизии.
- `PackageClosureResolver.invalidatePackage(packageId): void` — вычищает `fileBytes` по префиксу пакета.
- `PackageDeliveryService.invalidateArtifacts(packageId): Promise<void>` — удаляет `<packageRoot>/runtime` целиком (пересборка ленивая, при следующем запросе манифеста), и `invalidatePackage(packageId)` — вызывает `invalidateArtifacts` и `resolver.invalidatePackage` одним вызовом: `ScriptingPackagesService` знает только `PackageDeliveryService`, отдельный резолвер туда не инжектится.
- `PackageRevisionDispatcher.packagesChanged(packageIds: number[]): Promise<void>` и его реализация `PackageSyncService.packagesChanged(ids)` — сброс/переотправка состояния рантаймов комнаты. Вызывает `ScriptingPackagesService` через уже инжектированный диспетчер: `notifyPackagesChanged` в `PackageRevisionsService` не нужен, потому что `ScriptingPackagesService` не может его инжектировать (цикл `PackageRevisionsService → ScriptingPackagesService`).

Pins (`pins/<revision>.json`) не пересчитываются: и у переименованного пакета, и у зависимых цель ссылки — тот же `(packageId, revision)`; меняется только строка slug, а ключ артефакта от slug не зависит.

### 7.5. Переименование в редакторе

Новая операция моста, а не композиция `collect`/`replace` (та теряет `.uid`/`.import`):

- `package_fs.gd`: `op_rename({packageSlug, newSlug})` — проверить оба slug, отказать, если исходной папки нет или целевая папка **непустая**, пустую целевую удалить и переиспользовать, сделать `DirAccess.rename_absolute(package_dir(old), package_dir(new))`, затем пройти по перемещённому дереву и в текстовых файлах (`.gd/.tscn/.tres/.import`) заменить `res://packages/<old>/` на `res://packages/<new>/` (только целый slug), вернуть `{ rewritten: [...] }`. Непустая цель — ошибка `slug_target_not_empty` («В редакторе уже есть папка <new>; переименуйте или удалите её»).
- `plugin.gd`: `"rename"` в `VALID_OPS` и в `match` диспетчера.
- `godot-packages-fs.ts`: `renamePackage(from, to)` в типе `PackageFileSystem` и реализации; вызывает `bridge.call("rename", ...)`, затем `sync()` (персистентность), но **не** `rescan` — rescan делает хук, как в `createPackage`/`removePackage`.

Порядок в `use-room-packages` при сохранении формы:

0. Preflight в браузере: `files.exists(newSlug)` и `snapshot(newSlug)` непустой → форма блокируется с подсказкой «В редакторе уже есть папка <new>»; пустая папка не блокирует.
1. `PATCH` (при 409 с зависимостями — подтверждение и повторный PATCH с `confirmSlugRename`).
2. `dispatch({ type: 'updated', ... })` с новым slug, чтобы `slugOf` уже резолвил новое имя; перемапить `createdSlugsRef`.
3. Если `files.exists(oldSlug)` — `renamePackage(oldSlug, newSlug)`.
4. `requestEditorRescan()`.
5. `refresh(true)` (полная перезагрузка, не 10-секундный поллинг), чтобы `inEditor` и статусы пересчитались по новому slug.

`loadedRef` не трогаем: он ключуется по `packageId`, а относительные пути и хеши при переименовании не меняются, поэтому «локальные изменения» остаются корректными. Пере-сев через `adoptPackage` запрещён (сбросил бы `revision` к 0 и сломал `emitPackage`).

Если шаг 3 упал (мост недоступен, папка занята), сервер уже переименован: показываем ошибку с кнопкой «Повторить переименование папки»; повтор идемпотентен (старой папки нет, новая есть → успех). Старая папка остаётся сиротой до повтора.

### 7.6. Workshop-запись и переименование

Workshop-запись (глобальная строка) при переименовании пакета комнаты не меняется: связь между ними не хранится (при публикации `parentPackage` не ставится). Следствия, которые нужно озвучить в UI-подсказке диалога:

- Публикация переименованного пакета создаст запись под новым slug; старая запись останется в workshop, пока её не удалят.
- Пакет, добавленный из workshop (`parentPackage` = запись), после переименования остаётся копией с тем же `parentPackage`; slug копии и записи расходятся — это допустимо, `parentPackage` хранит идентичность (`id`), а не имя.

## 9. Risks

- **Сиротская таблица** `retired_package_slug` остаётся в БД. Безвредно; удаляется вручную.
- **Осиротевшая папка в рантайме комнаты**: `packages_manager.gd` запоминает новый slug (`_remember_slug`) и работает с ним, но старая папка `packages/<old>` остаётся мусором до пересоздания комнаты. Не влияет на корректность.
- **`.import` и импорт ресурсов**: мост переписывает `source_file`, но Godot всё равно переимпортирует перемещённые ассеты при `scan()`; возможны временные предупреждения в консоли редактора.
- **Зависимые пакеты**: серверные published-байты переписываются (комнаты продолжают работать без перепубликации), но копии в редакторах авторов остаются со старым slug. При следующей публикации такого пакета его ссылка снова станет `res://packages/<old>/`, и сервер либо вернёт `package_dependency_unknown_slug:<old>` (если глобальной записи с этим slug нет), либо — что хуже — тихо срезолвит ссылку в глобальную workshop-запись с тем же slug (room-first, затем global). Второй случай закрывается предупреждением в диалоге подтверждения и подсказкой «обновите ссылки в пакетах: X, Y»; UI не может править чужие редакторы.
- **Крах между свапом деревьев и коммитом**: `.old`-деревья остаются на диске, а БД указывает на старые байты — пакет читается корректно; при следующем переименовании `.old` перезаписывается. Ошибка не «тихая»: она логируется.
- **Артефакты удалены, но клиент держит старый ключ**: получит 404 на файл и перезапросит манифест при следующей отправке/ретрае; это уже существующее поведение (`resolveRuntimeFile` не пересобирает).

## 10. Decisions log

- Пользователь: slug редактируется в любой момент, с переписыванием (вариант B).
- Пользователь: переиспользование удалённых workshop-slug разрешено.
- Пользователь: редактирование информации о пакете вынесено из панели публикации в отдельную панель из more-меню.
- Принято мной: удалить сущность tombstone, а не оставлять мёртвый код; таблицу не дропать автоматически.
- Принято мной: переименование — часть `PATCH`, а не отдельный эндпоинт (одна форма — один запрос, одна ошибка).
- Принято мной: published-байты зависимых пакетов той же комнаты переписываются, но только после подтверждения со списком; их локальные копии в редакторах не трогаются.
- Принято мной: переименование доступно только пакетам комнаты; slug workshop-записи не редактируется.
- Принято мной: PATCH с переименованием атомарен — при 409 не сохраняется ни одно поле.
- Принято мной: переименование берёт те же блокировки публикации, что и `publish()`, по возрастанию package id.
- Принято мной: workshop-запись не переименовывается каскадом.
